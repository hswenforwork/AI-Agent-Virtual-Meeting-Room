## 測試環境的限制（先誠實說明，這節沒有變）

這個工作環境**沒有**：
- Docker daemon（無法跑本機 Supabase CLI 的完整堆疊：PostgREST／GoTrue／Realtime）
- 任何 Claude／GPT／Gemini 的 API key，也沒有 `deno` 執行檔
- 對你正式 Supabase 專案的存取權（也依照指示不能碰正式環境）

所以這份報告嚴格區分兩種驗證方式，**不混著講**：

- **「實際執行」**：真的在本機 PostgreSQL 跑過對應的 SQL／trigger／RPC，看到真實查詢結果或
  真實錯誤訊息，下面每一項都附執行方式。
- **「程式碼檢視」**：沒有 Deno／瀏覽器／真實 LLM 可以執行，逐行比對程式碼邏輯是否跟已經
  實際驗證過的 SQL 行為一致、型別是否通過 `tsc`。這種情況一定會明講「程式碼檢視」，不會
  講成「測試通過」。

## 一、已經真的執行、有結果的測試

### 0. 第二輪 review 修正：三項合併前問題

本機資料庫的固定裝置這次也修正到跟正式 schema 更一致（`rooms.owner_id`／`notes`/`tasks`/
`files.owner_id` 都補上 `on delete cascade`，才能真的測出帳號刪除的級聯行為），每次修改都
整個資料庫重建重跑。

#### 0.1 修正 A：決策 append-only trigger 不能擋住合法的 FK 級聯

| 測項 | 做法 | 結果 |
|---|---|---|
| **刪除決策的來源房間應該成功、決策應該保留** | 建一筆 `source_room_id` 指向房間 A 的決策，以 U1 身分 `delete from rooms where id=房間A` | ✅ 第一版這裡會直接失敗（`source_room_id` 被 append-only trigger 一併擋下，跟其他內容欄位混在一起判斷），修正後 `DELETE 1` 成功；決策還在，`source_room_id` 正確變成 `null`、`status` 仍是 `active` |
| 帳號還存在時，直接 `DELETE FROM decisions` 一律擋下 | U1／U2 身分各自嘗試直接刪除自己的決策 | ✅ `DELETE 0`（RLS 沒有 delete policy），決策確認還在 |
| **刪除帳號本身，應該成功級聯刪除該帳號名下所有決策**（含互相取代的一對）| 幫 U2 建立兩筆互相取代的決策（D2 supersedes D1，D1 已經是 `superseded`），再以 U2 身分 `delete from profiles where id=U2` | ✅ 第一版這裡會直接失敗（DELETE 一律報錯，等於「使用者只要建立過一筆決策就永遠沒辦法刪除自己的帳號」）。修正後用 `pg_trigger_depth() > 1` 判斷「這次刪除是不是從另一個 trigger context 觸發的級聯」，`DELETE 1` 成功，U2 的 profile／rooms／decisions 事後查詢全部剩 0 筆，兩筆互相取代的決策（自我參照的外鍵）也正確一起被刪除，沒有外鍵違反錯誤 |

#### 0.2 修正 B：verified 來源必須由資料庫讀取，不能信任 payload／RPC edits

| 測項 | 做法 | 結果 |
|---|---|---|
| **RPC `edits` 參數偽造 `source_excerpt` 應該被完全忽略** | 建一則沒有帶 `source_excerpt` 的提案，呼叫 `accept_knowledge_proposal(id, '{"source_excerpt":"【偽造內容，不應該出現在資料庫】"}')` | ✅ 產生的 `knowledge_sources.content_snapshot` 是資料庫裡那則訊息**真實的內容**（「這是資料庫裡真實的訊息內容，不是偽造的。」），偽造文字完全沒有出現在結果裡；`insert_message_source_if_owned()` 已經改成完全不接受 `p_source_excerpt`／`p_source_room_id` 參數，摘要與 `room_id` 都是函式內部重新 `join messages/rooms` 讀出來的 |
| 來源 `room_id` 也是從訊息實際所在房間讀出來的 | 同上一筆結果 | ✅ `knowledge_sources.room_id` 正確等於那則訊息當下的 `room_id`，不是任何呼叫端傳入的值（函式簽名已經沒有這個參數可以傳） |

#### 0.3 修正 C：`knowledge_sources` 需要 owner 過濾與同帳號驗證

| 測項 | 做法 | 結果 |
|---|---|---|
| **U2 想替 U1 的知識偽造一筆「已驗證」來源** | U2 身分直接 `insert into knowledge_sources (owner_id=自己, subject_id=U1的知識id, verified=true, content_snapshot='偽造的已驗證內容', ...)` | ✅ 新增的 `validate_knowledge_source_subject()` trigger 擋下：`ERROR: 找不到這則來源指向的知識或決策`（RLS 讓 U2 連 U1 的知識都查不到，trigger 再確認一次，雙重防護，錯誤訊息也不會洩漏「這筆 id 其實存在、只是不是你的」）；U1 那筆知識底下確認完全沒有這筆偽造來源 |
| U1 自己替自己的知識加來源，仍然正常 | U1 身分 insert 一筆 `subject_id` 是自己知識的來源 | ✅ 成功 |
| `fetchCitableSources()` 讀取端也加上 `owner_id` 過濾 | 程式碼修改：`knowledgeContext.ts` 的查詢多一個 `.eq("owner_id", ownerId)` | 程式碼檢視＋既有的跨帳號隔離測試（見下面 2.1 第 6 點）間接涵蓋；寫入端的 trigger 已經讓「跨帳號偽造來源」這個情境在資料庫層就不可能發生，這裡是額外一層防護 |

#### 2.2 Review 修正 2／4：新增的 trigger／RPC 安全邏輯（這次新增的測試）

用兩個帳號 U1／U2、一則 U1 聊天室裡的訊息、一則 U2 聊天室裡的訊息，逐項驗證：

| 測項 | 做法 | 結果 |
|---|---|---|
| 決策內容不能直接 UPDATE | `update decisions set decision_text=... where id=...` | ✅ `enforce_decision_append_only()` 擋下：`ERROR: 決策內容不能修改` |
| 決策不能直接 DELETE | `delete from decisions where id=...` | ✅ RLS 沒有 delete policy，`DELETE 0`；決策確認還在 |
| 取代不存在的決策 → 整筆新增操作失敗 | `insert into decisions (..., supersedes_id) values (..., '不存在的 id')` | ✅ `ERROR: 找不到要取代的決策`；新決策沒有被留下（`should_be_0` 查詢確認） |
| 決策不能取代自己 | `insert ... supersedes_id = 自己即將使用的 id` | ✅ `ERROR: 決策不能取代自己` |
| U2 想取代 U1 的決策（越權）| U2 身分 `insert ... supersedes_id = U1的決策id` | ✅ 失敗（RLS 讓 U2 的 session 連那筆決策都查不到，`ERROR: 找不到要取代的決策`——等於 RLS 跟 trigger 雙重擋下，U2 甚至無法用錯誤訊息分辨「不存在」跟「不是自己的」，避免枚舉其他帳號的決策 id） |
| 取代已經被取代過的決策 | D2 已經取代 D1 後，再讓 D3 想取代 D1 | ✅ `ERROR: 要取代的決策目前不是有效狀態` |
| **兩個交易同時搶著取代同一筆決策**（真正的併發測試，不是模擬）| 兩個獨立 `psql` 連線背景執行：交易 A 先 `insert ... supersedes_id=X` 後 `pg_sleep(3)` 才 `commit`；交易 B 晚 1 秒送出同一個 `supersedes_id=X` 的 insert | ✅ A 正常提交；B 的 `select ... for update` 被鎖住直到 A 提交，甦醒後看到 X 已經是 `superseded`，正確報錯回滾；最終資料庫只有 A 那筆是 `active`，B 完全沒有留下痕跡 |
| 提案確認時，來源訊息確實屬於同一帳號 | 透過 `accept_knowledge_proposal()` 確認一則提案（`insert_message_source_if_owned()` 內部重新讀取訊息內容，見上面 0.2 節） | ✅ 產生的 `knowledge_sources`：`verified=true`，`content_snapshot` 是資料庫當下讀到的真實訊息內容 |
| 來源訊息不存在（例如已經被刪除）| `source_message_id` 指向一則已經不存在的訊息 | ✅ 完全不留來源列（表示「這個提案沒有可查證的來源」），`verified` 這個欄位根本不會有機會被寫成 `true` |
| **提案的 `source_message_id` 被偽造成別人帳號的訊息**（安全測試）| `source_message_id` 指向 U2 聊天室裡的訊息，用 U1 身分確認 | ✅ `insert_message_source_if_owned()` 查出訊息所在房間的 `owner_id` 是 U2、不是 U1，直接跳過，**完全不留來源列**——U1 沒辦法假造一筆「已驗證」的來源，也沒有任何 U2 的訊息內容外洩到 U1 的資料 |
| **RPC `edits` 參數偽造 `source_excerpt`**（第二輪 review 修正，見上面 0.2 節）| 呼叫 `accept_knowledge_proposal` 時帶 `edits: {source_excerpt: '偽造內容'}` | ✅ 完全被忽略，`content_snapshot` 是資料庫讀到的真實內容 |
| 刪除來源聊天室後，透過提案產生的來源摘要仍然保留 | 對上面「驗證成功」那筆，刪除來源聊天室 | ✅ `status` 變 `invalid`、`message_id` 變 `null`，但 `content_snapshot` 沒有被清空 |

## 三、你部署後的驗收步驟（對照使用者原始描述的 6 個情境＋這次新增的功能）

1. 到 Supabase Dashboard 執行 `0019_shared_knowledge.sql`，等 GitHub Actions 部署完
   `knowledge-audit` 這個 Edge Function。
2. 在聊天室 A 打開「共享知識 → 背景」，新增一則知識並附上內容；打開「決策」，新增一項決策。
3. 切到聊天室 B（同一個帳號），打開「共享知識 → 背景／決策」，應該看到同一筆資料。在聊天室
   B 用 `@` 點名跟聊天室 A 不同的模型，問跟這則知識相關的問題，檢查它的回覆有沒有提到這則
   知識的內容、有沒有附上來源連結；點那個連結，確認真的跳到聊天室 A 並短暫高亮那則訊息
   （如果訊息比較舊、還沒被載入到聊天室的分頁視窗內，目前不會自動跳過去，這是已知限制）。

# 跨聊天室共享知識系統：測試報告

日期：2026-09-23
範圍：`supabase/migrations/0019_shared_knowledge.sql`、`supabase/functions/_shared/knowledgeContext.ts`、
`supabase/functions/_shared/knowledgeProposal.ts`、`supabase/functions/knowledge-audit/`、
`src/features/knowledge/*`、`agent-run`／`worker-task-start` 的知識注入

## 測試環境的限制（先誠實說明）

這個工作環境**沒有**：
- Docker daemon（無法跑本機 Supabase CLI 的完整堆疊：PostgREST／GoTrue／Realtime）
- 任何 Claude／GPT／Gemini 的 API key
- 對你正式 Supabase 專案的存取權（也依照指示不能碰正式環境）

所以「AI 真的在回覆裡正確引用知識」這件事，**無法在這個環境裡對著真正的 LLM 執行一次拿到真
實回覆**。有做到、也已經確認的是：**組出系統提示詞的那段程式邏輯本身是正確的**（下面測試 2
用跟程式碼完全一樣的 SQL 條件跑過），加上這段文字最終怎麼接進 `systemPrompt`（純字串串接，
見 `agent-run/index.ts`）本身沒有特殊邏輯，跟現有的 `buildWorkspaceContext()`（記事本/待辦
事項那段，已經上線在跑）是同一種串接方式。真正端對端（含 LLM 是否遵照）的驗證，需要你部署
後在正式環境用真實帳號測一次——下面「你部署後的驗收步驟」提供逐項對照。

## 已經真的執行、有結果的測試

### 1. Migration 本身可以乾淨套用

在本機起了一個 PostgreSQL 16（`apt` 內建套件，非 Supabase CLI），建立最小夠用的固定裝置
（`auth.uid()`、`profiles`/`rooms`/`agents`/`messages`/`notes`/`tasks`/`files` 的必要欄位），
直接套用 `supabase/migrations/0019_shared_knowledge.sql`（沒有修改內容）：

```
$ psql -f 0019_shared_knowledge.sql
CREATE TABLE / CREATE INDEX / ALTER TABLE / CREATE POLICY / CREATE FUNCTION / CREATE TRIGGER ...
（全部成功，沒有任何 ERROR）
```

### 2. 用真正會被 RLS 限制的非特權角色跑功能測試

建立一個 `nosuperuser nobypassrls` 的角色（模擬 Supabase 的 `authenticated` 角色，這點很重要——
用 superuser 測試 RLS 會因為 bypass 而測不出真正的隔離效果），依序驗證：

| # | 對應使用者的端到端測試情境 | 測試內容 | 結果 |
|---|---|---|---|
| 1 | 聊天室 A 確認一則有來源的知識與一項決策 | 以 U1 身分 insert `knowledge_items`＋`knowledge_sources`＋`decisions` | ✅ 三筆都寫入成功，`knowledge_sources.verified=true`、`status=valid` |
| 2 | 聊天室 B 點名另一家模型，它能正確引用 | 執行跟 `knowledgeContext.ts` 的 `fetchRelevantKnowledgeItems`/`fetchRelevantDecisions` 完全一樣的 SQL 條件（`owner_id`＋`status='active'`＋未過期／`decided_at` 排序），**不依 `room_id` 篩選** | ✅ 查得到聊天室 A 建立的知識與決策——因為資料本身是依帳號存放，任何聊天室查都是同一份 |
| 3 | 建立關聯後兩邊看到同一張圖 | insert `knowledge_links`（決策 supports 知識） | ✅ 建立成功；也驗證了自我關聯會被 `validate_knowledge_link()` trigger 擋下（`ERROR: 不能建立自我關聯`） |
| 4 | 取代舊決策後模型使用新版本 | insert 一筆 D2，`supersedes_id=D1` | ✅ `handle_decision_supersede()` trigger 自動把 D1 標成 `superseded`、回填 `superseded_by_id`；再跑一次跟第 2 點一樣的檢索查詢，**只回傳 D2，不再回傳 D1** |
| — | 代理提案 → 使用者確認才變正式知識 | insert `knowledge_proposals`，呼叫 `accept_knowledge_proposal()` | ✅ 確認前 `knowledge_items` 是 1 筆，確認後變 2 筆；`knowledge_proposals.status` 正確變成 `accepted` 並回填 `resolved_knowledge_item_id`；另外測試 `reject_knowledge_proposal()` 也正確把狀態改成 `rejected` |
| 5 | 刪除來源聊天室後，知識仍然存在 | `delete from rooms where id = 聊天室A` | ✅ `knowledge_items` 筆數不變、內容不變，只有 `source_room_id` 被 set null；對應的 `knowledge_sources` 那筆的 `message_id` 也被 set null，且 `status` 自動被 `mark_knowledge_source_invalid()` trigger 改成 `invalid`，但 `content_snapshot`（先前驗證過的摘要）**沒有被清空** |
| 6 | 另一個帳號無法讀取 | 切換到 U2 身分查詢 `knowledge_items`/`decisions`/`knowledge_links`/`knowledge_proposals`/`knowledge_sources` | ✅ 全部回傳 0 筆；U2 嘗試呼叫 `reject_knowledge_proposal()` 拒絕 U1 的提案會直接報錯（`ERROR: 找不到這個待確認的提案，或不屬於自己`），事後確認 U1 視角下那筆提案沒有被 U2 動到 |

另外針對 `knowledge-audit` 的稽核邏輯，用同一個測試資料庫補測了兩個核心查詢：

- 「沒有來源的知識」：新建一筆刻意不附來源的知識，查詢正確抓到；先前已附來源的知識沒有被
  誤判。
- 「已過期的知識」：新建一筆 `expires_at` 設在昨天的知識，查詢正確標示 `is_expired = true`。

## 沒有做、也做不到的測試（誠實列出）

1. **真的請 Claude／GPT／Gemini 回覆一次，確認它有引用知識內容**：需要真實 API key 與部署後的
   Edge Function，這個環境沒有。已驗證的是「餵給它的文字本身是對的」，不是「它讀了之後真的照
   著回答」——後者是模型能力本身的問題，跟這個功能的程式邏輯無關，也是這個專案所有既有 context
   注入功能（記事本／待辦事項／對話摘要）共同的既有信任邊界，不是這次新增的風險。
2. **瀏覽器互動測試**（點「共享知識」分頁、確認提案按鈕、拖曳關聯圖）：需要真實 Supabase 專案
   （PostgREST／GoTrue／Realtime），這個環境沒有 Docker 也沒有正式專案存取權，無法起一個能真正
   登入、查詢的前端環境。已驗證的是元件能通過型別檢查與建置，UI 邏輯（哪個按鈕呼叫哪個 mutation）
   經過人工逐行檢視。
3. **排程稽核（pg_cron）**：README 只提供設定 SQL，沒有在任何專案裡真的執行過（依照指示不碰正式
   Supabase，且排程也刻意不主動啟用）。

## 你部署後的驗收步驟（對照使用者原始描述的 6 個情境）

1. 到 Supabase Dashboard 執行 `0019_shared_knowledge.sql`，等 GitHub Actions 部署完
   `knowledge-audit` 這個新 Edge Function。
2. 在聊天室 A 打開「共享知識 → 背景」，新增一則知識並附上內容；打開「決策」，新增一項決策。
3. 切到聊天室 B（同一個帳號），打開「共享知識 → 背景／決策」，應該看到同一筆資料（不用重新
   輸入）。在聊天室 B 用 `@`點名跟聊天室 A 不同的模型，問跟這則知識相關的問題，檢查它的回覆
   有沒有提到這則知識的內容。
4. 在「共享知識 → 關聯圖」用「新增關聯」把知識和決策連起來；重新整理頁面（或切到另一個聊天
   室再打開），確認看到同一條線。
5. 在「決策」分頁新增一項決策，選擇「取代既有決策」指向第 2 步那項；之後點名模型問同一個
   主題，確認它的回覆是依照新決策、不是舊的。
6. 刪除聊天室 A（左側聊天室清單的刪除功能）；打開「共享知識 → 背景」確認知識還在，只是不再
   顯示「來自：聊天室 A」。
7. 用另一個帳號登入，打開「共享知識」分頁，應該完全看不到上面任何一筆資料。

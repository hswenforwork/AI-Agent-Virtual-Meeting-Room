## 測試環境的限制（先誠實說明，這節沒有變）

這個工作環境**沒有**：
- Docker daemon（無法跑本機 Supabase CLI 的完整堆疊：PostgREST／GoTrue／Realtime）

所以這份報告嚴格區分兩種驗證方式，**不混著講**：

- **「實際執行」**：真的在本機 PostgreSQL 跑過對應的 SQL／trigger／RPC，看到真實查詢結果或
  真實錯誤訊息，下面每一項都附執行方式。

## 一、已經真的執行、有結果的測試

### 0. 第二、三輪 review 修正：五項合併前問題

本機資料庫的固定裝置這次也修正到跟正式 schema 更一致（`rooms.owner_id`／`notes`/`tasks`/
`files.owner_id` 都補上 `on delete cascade`，才能真的測出帳號刪除的級聯行為），每次修改都
整個資料庫重建重跑。

#### 0.1 修正 A：決策 append-only trigger 不能擋住合法的 FK 級聯

| 測項 | 做法 | 結果 |
|---|---|---|
| **刪除決策的來源房間應該成功、決策應該保留** | 建一筆 `source_room_id` 指向房間 A 的決策，以 U1 身分 `delete from rooms where id=房間A` | ✅ 第一版這裡會直接失敗（`source_room_id` 被 append-only trigger 一併擋下，跟其他內容欄位混在一起判斷），修正後 `DELETE 1` 成功；決策還在，`source_room_id` 正確變成 `null`、`status` 仍是 `active` |
| 帳號還存在時，直接 `DELETE FROM decisions` 一律擋下 | U1／U2 身分各自嘗試直接刪除自己的決策 | ✅ `DELETE 0`（RLS 沒有 delete policy），決策確認還在 |
| **刪除帳號本身，應該成功級聯刪除該帳號名下所有決策**（含互相取代的一對）| 幫 U2 建立兩筆互相取代的決策（D2 supersedes D1，D1 已經是 `superseded`），再以 U2 身分 `delete from profiles where id=U2` | ✅ 第一版這裡會直接失敗（DELETE 一律報錯，等於「使用者只要建立過一筆決策就永遠沒辦法刪除自己的帳號」）。修正後的判斷條件見下面 0.4 節，`DELETE 1` 成功，U2 的 profile／rooms／decisions 事後查詢全部剩 0 筆，兩筆互相取代的決策（自我參照的外鍵）也正確一起被刪除，沒有外鍵違反錯誤 |

#### 0.4 修正 D／E（第三輪 review）：`status`／`superseded_by_id` 也要保護，DELETE 的放行條件要更精確

**問題 D：** append-only trigger 保護了 `title`／`decision_text` 等內容欄位，卻沒有把
`status`、`superseded_by_id` 這兩個欄位列進去——這兩個欄位剛好又是 `decisions_update_own`
RLS policy 允許使用者自己更新的範圍內，等於使用者可以直接
`update decisions set status='superseded' where id=...`，完全不用真的新增一筆
`supersedes_id` 指向它的新決策，決策就會從 `buildKnowledgeContext()` 的 `status='active'`
檢索範圍消失，卻沒有留下「被誰取代、為什麼」的紀錄。

**問題 E：** 第二輪修正 DELETE 用 `pg_trigger_depth() > 1` 判斷「是不是合法級聯」，但這個
函式的定義只回傳「目前巢狀在幾層 trigger 裡」，不保證巢狀的原因就是帳號被刪除——理論上任何
未來從別的 trigger context 觸發的 DELETE 都會符合這個條件。

**修正方式：**
- `status`／`superseded_by_id` 的變動：改用一個交易層級的 GUC
  （`app.decisions_supersede_update`）當明確旗標，只有 `handle_decision_supersede()`
  這個函式自己在執行合法的取代更新時才會設定它（用完立刻關掉，把允許的視窗縮到只有那一個
  `UPDATE` 陳述式），使用者或任何其他路徑直接改這兩個欄位一律擋下——不是靠「巢狀」這種
  間接訊號，是靠這個函式自己明確宣告「這是我在做的合法操作」。
- DELETE：從單純 `pg_trigger_depth() > 1` 改成兩個條件都要成立：`pg_trigger_depth() > 1`
  **且** `not exists (select 1 from profiles where id = old.owner_id)`——後者才是真正對應
  「帳號正在被刪除」這個實際情況的條件（這一列的擁有者，在這個交易當下，查不到對應的
  `profiles` 列），trigger 深度只當第二層佐證。

**用真實證據驗證這兩個條件的值，不只是相信邏輯推導**：暫時在 trigger 裡加一行
`raise notice` 印出 `pg_trigger_depth()` 與 `exists(select 1 from profiles ...)` 的實際
值，分別跑「一般使用者直接 DELETE」跟「帳號刪除觸發的級聯 DELETE」兩種情境：

```
一般使用者直接 DELETE（帳號還在）：RLS 沒有 delete policy，DELETE 0，trigger 根本沒有機會
                                   執行到（沒有符合 RLS 的列可以刪，這本身就是另一層防護）。
帳號刪除觸發的級聯 DELETE：
  NOTICE:  DEBUG DELETE: pg_trigger_depth()=2 profile_exists=f
```

證實了修正後的組合條件在這兩種情境下確實給出正確的判斷依據；驗證完就把 debug 版本換回沒有
`raise notice` 的正式版本（跟這次提交的 migration 檔案一致）。

| 測項 | 做法 | 結果 |
|---|---|---|
| **直接 `UPDATE decisions SET status='superseded'`** | 一般登入角色，帳號還在，對自己名下的決策執行 | ✅ `ERROR: 決策的狀態只能透過新增一筆帶 supersedes_id 的決策來改變，不能直接修改`；決策的 `status` 確認沒有被改動 |
| **直接 `UPDATE decisions SET superseded_by_id=...`** | 同上，改另一個欄位 | ✅ 同樣被擋下；`superseded_by_id` 確認沒有被改動 |
| 正常取代流程（`insert` 一筆帶 `supersedes_id` 的新決策）仍然成功 | 重新測一次原本的「D2 取代 D1」流程 | ✅ D1 正確被自動標成 `superseded`、`superseded_by_id` 指向 D2；沒有被上面的新保護誤擋 |
| 刪除聊天室（決策的來源房間）仍然成功 | 重新測一次 | ✅ `DELETE 1` 成功，決策保留 |
| 帳號還存在時，直接刪除決策仍然被擋 | 重新測一次 | ✅ `DELETE 0` |
| 刪除帳號本身（含互相取代的一對決策）仍然成功 | 重新測一次 | ✅ `DELETE 1` 成功，該帳號的 profile／decisions 事後查詢全部 0 筆 |

#### 0.5 第四輪修正：`app.decisions_supersede_update` 這個 GUC 旗標本身可以被繞過 → 改用資料庫權限（REVOKE）當真正邊界

**使用者實測回報的漏洞：** 0.4 節用的「交易層級 GUC 旗標」設計有一個根本問題——
`app.*` 是 PostgreSQL 任何角色都能在自己交易裡自由 `set_config()` 的一般自訂參數，
不是任何形式的祕密或特權標記。也就是說，一般登入角色自己就能做：

```sql
begin;
select set_config('app.decisions_supersede_update', 'true', true);
update public.decisions set status = 'superseded' where id = '自己的有效決策 id';
rollback;
```

**先重現這個漏洞，確認它是真的**（用修正前、也就是 0.4 節版本的 migration，一般登入角色
`authenticated`，非 superuser、非 bypassrls）：

```
BEGIN
 set_config
------------
 true
UPDATE 1        -- 修正前：這裡會成功，證明旗標確實可以被繞過
ROLLBACK
```

`UPDATE 1` 證實了修正前的設計確實可以被繞過（測試完 `rollback`，沒有留下實際被竄改的資料）。

**真正的修法：** 拿掉這個可被繞過的旗標判斷，改成資料庫權限系統本身的邊界——

```sql
revoke update on public.decisions from authenticated, anon, service_role;
```

之後任何一般角色想對 `decisions`執行任何 `UPDATE` 陳述式，都會在陳述式本身被資料庫直接
拒絕（`permission denied for table decisions`），連一行都不會被處理到，trigger 根本沒有
機會執行——這是 PostgreSQL 權限系統本身的邊界，不是任何可以被 session/交易變數繞過的邏輯
判斷。唯一還能合法改變 `status`／`superseded_by_id` 的路徑，是 `handle_decision_supersede()`：
這個函式改成 `security definer set search_path = public`，用函式擁有者（執行 migration 的
角色，正常是 Supabase 專案的 postgres/owner）的權限執行內部的 `UPDATE`，不受這個 `revoke`
影響。

`enforce_decision_append_only()` trigger 保留下來，但已經不是「靠一個旗標判斷」，改成
「這個 status/superseded_by_id 的變化，是否剛好對應一筆真實存在、指回這一列的取代決策」——
也就是 `handle_decision_supersede()` 唯一會做的那種變化。這個 trigger 現在明確定位是
**第二層、非權威性**的防禦（belt-and-suspenders）：真正的邊界是上面的 `revoke`；trigger
只是萬一未來有人不小心把 `UPDATE` 權限重新 grant 回去時的次一層防線。

**修正過程中額外發現、一併修正的連帶問題：** `validate_decision_supersede()`（取代前驗證
目標決策存在、屬於自己、目前是 `active` 的那個 trigger 函式）原本用 `select ... for update`
鎖住目標那一列防止併發取代——這個 `for update`（`for share` 也一樣，已經實測驗證過）在
PostgreSQL 裡除了 `SELECT` 權限，**還額外要求呼叫者對目標表有 `UPDATE` 權限**，跟這個鎖定
子句最終會不會真的執行 `UPDATE` 無關，是鎖定子句本身的權限規則。`revoke update` 之後，這個
函式（原本不是 `security definer`）會讓一般使用者連合法的「新增一筆取代決策」都做不到——
insert 觸發這個 `before insert` trigger 就直接 `permission denied for table decisions`。
這是先套用 `revoke` 之後、透過完整回歸測試才發現的真實迴歸（不是憑空推論），所以把這個函式
也一起改成 `security definer`。附帶影響：如果 `supersedes_id` 指向別人的決策，原本
（非 definer）RLS 會讓這裡的 `select` 直接看不到那一列（回報「找不到要取代的決策」）；
`security definer` 繞過 RLS 後，這裡看得到那一列、能判斷 `owner_id` 不符，回報更精確的
「不能取代不屬於自己的決策」——這只是錯誤訊息內容的差異（洩漏「這個 id 存在」，不洩漏
決策內容），操作本身一樣會被擋下、不會建立任何新決策，攻擊者要利用這點得先猜中別人一筆
決策的 uuid（128 bit 隨機值）。下面表格第 4 項的實測結果就是這個訊息。

**本機測試環境為了讓這個測試有意義，額外補的固定裝置：** 之前幾輪的本機測試只用一個
`app_user` 登入角色，沒有真的建立 Supabase 的 `authenticated`／`anon`／`service_role`
三個角色，`revoke ... from authenticated, ...` 在那個固定裝置裡根本沒有對象可以擋。
這次補上：

```sql
create role authenticated login nosuperuser nobypassrls;
create role anon nosuperuser nobypassrls;
create role service_role nosuperuser bypassrls;
grant usage on schema public to authenticated, anon, service_role;
grant all on all tables in schema public to authenticated, anon, service_role;   -- 模擬固定裝置既有資料表
alter default privileges for role postgres in schema public
  grant all on tables to authenticated, anon, service_role;                      -- 模擬 migration 建的新表也自動有基準權限
```

這模擬的是 Supabase 專案層級「標準角色 + 預設權限」這個平台既有設定（正式環境是專案建立時
就設好的，這個 repo 其他 migration 也都沒有明文 `grant`，只有這次因為要 `revoke`，才需要在
本機測試環境先把這個基準建出來，讓 `revoke` 是「從既有權限扣掉一項」，不是「本來就沒有權限，
revoke 沒有意義」）。測試時用 `set role authenticated;`（在 superuser 連線裡切換角色，跟
Supabase PostgREST 內部用 `SET ROLE authenticated` 模擬每個請求角色的機制一致，比額外開一個
獨立登入角色更貼近正式環境）。

   連結格式、`recordKnowledgeProposal()` 呼叫 `accept_knowledge_proposal` 的邏輯、

   證實過的 SQL 行為一致、`tsc` 型別檢查通過），不是「執行後看到正確結果」。上面第一節每次
   寫「程式碼檢視」都是指這件事。
2. **真的請 Claude／GPT／Gemini 回覆一次，確認它有引用知識來源並附上連結**：需要真實 API
   key 與部署後的 Edge Function，這個環境沒有。**「模型真的在回覆裡引用並讓使用者點得回去」
   這件事本身沒有測過**，需要你部署後實際測一次。

## 三、你部署後的驗收步驟（對照使用者原始描述的 6 個情境＋這次新增的功能）

1. 到 Supabase Dashboard 執行 `0019_shared_knowledge.sql`，等 GitHub Actions 部署完
   `knowledge-audit` 這個 Edge Function。
2. 在聊天室 A 打開「共享知識 → 背景」，新增一則知識並附上內容；打開「決策」，新增一項決策。
3. 切到聊天室 B（同一個帳號），打開「共享知識 → 背景／決策」，應該看到同一筆資料。在聊天室
   B 用 `@` 點名跟聊天室 A 不同的模型，問跟這則知識相關的問題，檢查它的回覆有沒有提到這則
   知識的內容、有沒有附上來源連結；點那個連結，確認真的跳到聊天室 A 並短暫高亮那則訊息
   （如果訊息比較舊、還沒被載入到聊天室的分頁視窗內，目前不會自動跳過去，這是已知限制）。
4. 在「共享知識 → 關聯圖」用「新增關聯」把知識和決策連起來（可以試著建一條「矛盾」關聯）；
   重新整理頁面（或切到另一個聊天室再打開），確認看到同一條線；點名模型問到相關主題時，
   確認它的回覆有提到這條矛盾、沒有自己選一邊當標準答案。
5. 在「決策」分頁新增一項決策，選擇「取代既有決策」指向第 2 步那項；之後點名模型問同一個
   主題，確認它的回覆是依照新決策、不是舊的；也試著再對已經被取代的那筆決策按「取代」，
   確認畫面上會出現錯誤（不會讓兩筆同時生效）。
6. 讓代理在聊天中主動提出一則知識提案（明確跟它說「這件事以後要記住」之類的），到「提案」
   分頁確認；確認前該筆知識不存在，確認後才出現，且如果代理有帶上摘要，來源會顯示「已驗證」。
7. 刪除聊天室 A；打開「共享知識 → 背景」確認知識還在，只是不再顯示「來自：聊天室 A」；打開
   該筆知識的來源清單，確認來源標示「已失效」但摘要還在。
8. 用另一個帳號登入，打開「共享知識」分頁，應該完全看不到上面任何一筆資料。
9. （選用）依 README 設定一次排程稽核，確認排程觸發時能成功產生報告；也可以刻意造一筆沒有
   來源的知識，確認手動或排程稽核都能抓到。
10. （選用，風險較高，建議用測試帳號）確認過刪除聊天室不會影響決策後，再確認「刪除帳號」
    本身仍然可以正常完成——這是第二輪 review 抓到的問題：第一版的 trigger 會讓「只要建立過
    一筆決策，帳號就永遠刪不掉」，本機測試已經證實修正後級聯刪除能成功，但正式環境的刪除
    帳號流程（如果有）建議還是實際跑一次確認。
11. **第四輪新增，建議優先做**：套用 migration 後，用 SQL Editor（登入為專案 owner／
    postgres，等同這份報告本機測試裡的角色）跑一次
    `select grantee, privilege_type from information_schema.role_table_grants where
    table_name='decisions' and grantee in ('authenticated','anon','service_role');`，
    確認結果裡沒有任何一列 `privilege_type='UPDATE'`（本機測試在乾淨環境下確認過結果是
    這樣，但正式 Supabase 專案的預設權限設定理論上跟本機模擬的固定裝置未必完全一致，值得
    實際查一次）。接著在畫面上完整走一次「新增決策 → 用『取代既有決策』新增第二筆」的流程，
    確認正常成功（這是 `revoke` 之後唯一還會執行 `decisions` 相關寫入的合法路徑，本機已經
    測過，但正式環境的 PostgREST／RLS 角色映射建議還是實際點一次確認沒有連帶破壞）。

## 1. 一句話定義（更新版）

「AI 協作室」是一個瀏覽器聊天室：使用者可以在同一個對話視窗中，用 `@供應商`（如 `@GPT`、`@Claude`、`@Gemini`）點名不同 AI 供應商，讓它們針對同一個問題平行給出各自的答案並排比較——把使用者現在「手動開多個分頁互相丟問題」的動作，整合進一個介面。沒有點名時，預設由「主管代理」（MVP 階段＝Claude）回覆。右側搭配記事本、待辦事項與檔案夾（可作為多供應商共享的上下文），相簿與行事曆延後到之後的版本。

**與 v1 最大的不同**：v1 的核心是「角色分工代理」（主管/研究/程式/測試，四者共用同一個 Gemini 模型），多供應商是「未來功能」。v2 反過來——**多供應商是核心，角色分工是次要／暫不做**。

## 2. 與 v1 規劃的差異總覽

| 面向 | v1（原始規劃） | v2（訪談後調整） | 對應訪談 |
|---|---|---|---|
| 核心價值 | 角色分工協作（主管/研究/程式/測試） | 多供應商平行比較（GPT/Claude/Gemini 互相補位） | Q1, Q2 |
| 代理設計 | 4 個角色代理，第一版共用同一 Gemini 模型 | 代理＝供應商（GPT-agent、Claude-agent、Gemini-agent），主管代理＝Claude（暫定） | Q2, Q5, Q6 |
| 成本前提 | 零成本（GitHub Pages＋Supabase Free＋Gemini 免費層） | 非硬性零成本；AI API 預算 US$30/月起，可彈性加碼；資料庫/託管優先免費，必要時另編預算 | Q3, Q4, Q11 |
| AI 供應商 | 只接 Gemini（其餘供應商列為第二階段） | 目前已有 Anthropic API key；OpenAI／Google 的 API key **尚未申請**，需另外辦理 | Q3, Q4 |
| 使用範圍 | 未明確定義（文件通篇假設多人房間） | 主要自己用，保留未來小範圍分享給朋友/同事的可能性 | Q7 |
| 權限設計 | 完整 4 級角色權限（owner/admin/member/viewer）＋精細 RLS | 保留基本帳號＋房間結構，但不需要一次做滿完整權限矩陣 | Q7 |
| 開發環境前提 | 公用電腦、不可安裝軟體、僅瀏覽器 | **維持不變**，文件第 17 節雲端開發方式仍然適用 | Q8 |
| 右側工具（MVP） | 相簿＋檔案＋記事本＋行事曆＋待辦，全部列入第 4-5 階段 | **MVP 只做**：記事本、待辦事項、檔案夾（含共享上下文）；相簿、行事曆延後 | Q9 |
| 檔案夾用途 | 主要是附件中繼資料＋（第二階段）文件檢索 | 檔案要能被多個供應商讀取當共享上下文（優先），同時也要能單純存放 | Q10 |
| 人工確認機制 | 所有中高風險寫入（含建立記事/待辦）都需確認卡 | 只有刪除／批次修改等難復原操作才需要確認卡；建立記事/待辦等低風險操作直接執行 | Q12 |

## 3. MVP 範圍（v2）

### 3.1 必須完成

1. 使用者可以登入／登出（沿用 Supabase Auth，單帳號為主，結構上預留多人）。
2. 建立至少一間協作室（room），結構上支援未來加入其他成員，但 MVP 不強求完整權限系統。
3. 同一對話視窗顯示使用者訊息，以及各供應商代理（Claude／GPT／Gemini）的回覆。
4. **點名路由（沿用 v1 六.2 節邏輯，主體改為供應商）**：
   - 沒有 `@`：只有「主管代理」（MVP＝Claude）回覆。
   - `@GPT`、`@Claude`、`@Gemini`（可複選）：只有被點名的供應商介入回覆，**主管代理當輪完全不參與、不總結、不仲裁**。
   - 多個供應商同時被點名時，各自獨立回答，**平行並排顯示**，不互相看到彼此答案（v2 第一版不做自動接力／仲裁，對應 v1 第 6 章的簡化版）。
5. 右側三個工具：**記事本、待辦事項、檔案夾**。
   - 檔案夾支援「上傳檔案→ 文字擷取 → 作為對話上下文餵給被點名的供應商」，也可單純存放檔案。
6. 低風險寫入（建立記事、建立待辦）**直接執行，不跳確認卡**；高風險操作（刪除檔案、批次修改／刪除）才彈出確認卡，並保留稽核紀錄（audit_logs）供事後查看。
7. 目前只接 **Claude（Anthropic API）**，作為第一階段唯一真正能動的供應商；GPT／Gemini 的 Provider Adapter 介面（沿用 v1 10.4 節設計）先寫好，但先以「尚未設定 API key／未啟用」狀態呈現於 UI，等申請好金鑰後再啟用，不阻塞第一階段上線。
8. 頁面重新整理／換裝置登入後，訊息、記事、待辦、檔案仍存在（Supabase 持久化）。
9. 手機與電腦瀏覽器都可使用（沿用 v1 5.1／5.2 節版面設計）。
10. 資料庫／API 金鑰只在後端（Supabase Edge Function secrets），前端與 GitHub 不得出現任何秘密值。

### 3.2 MVP 暫不做（比 v1 再收斂）

- 角色分工代理（研究/程式/測試代理）——如果之後真的需要，屬於「在多供應商之上再疊加角色語意」的擴充，不是 v2 第一階段目標。
- 完整多人房間權限（owner/admin/member/viewer 四級精細 RLS）——先做「一個使用者、一間房間」的最小可行版本，架構上不擋未來擴充。
- 相簿、行事曆。
- 自動接力／仲裁（系統自動判斷某供應商「解決不了」再轉發或統整答案）——先讓使用者自己看並排答案判斷，之後有需要再迭代。
- GPT、Gemini 的實際串接（介面先留，金鑰未備妥前不啟用）。
- MCP、向量搜尋、視訊語音——與 v1 一致，暫不做。

### 3.3 v2 成功標準

| 指標 | 驗收標準 |
|---|---|
| 多供應商點名 | `@Claude` 後只有 Claude 回覆；未來 `@GPT`／`@Gemini` 開通後同理 |
| 平行比較 | 同時點名多家時，各自答案獨立並排顯示，互不干擾、互不合併 |
| 主管代理不越界 | 其他代理被點名時，主管代理（Claude 值班身分）當輪不回覆、不插話 |
| 資料持久化 | 重新整理或換裝置登入後，訊息／記事／待辦／檔案仍在 |
| 共享上下文 | 上傳的檔案內容能被組進送給被點名供應商的 prompt |
| 低摩擦寫入 | 建立記事／待辦不用等確認卡；刪除／批次操作才跳確認卡 |
| 預算可控 | 有用量儀表板可看到 Claude API 當月花費，且落在 US$30 基準附近可控範圍 |
| 免安裝開發 | 全程可用 GitHub Codespaces／`github.dev`＋GitHub Actions 完成開發與部署，不需本機裝軟體 |

## 4. 技術棧（延用 v1，僅標註差異）

沿用 v1 第 3 章的整體選型（GitHub Pages＋React/TS/Vite＋Tailwind/shadcn＋Supabase Auth/DB/Realtime/Storage＋Supabase Edge Functions），差異如下：

- **AI 供應商**：v1 只接 Gemini；v2 第一階段只接 **Claude（Anthropic API）**，Provider Adapter 介面（v1 10.4 節）從第一階段就要落地，但實作只需完成 Claude 的 adapter，GPT／Gemini 的 adapter 先留空殼／型別定義。
- **模型選擇**：不再鎖定 Gemini Flash-Lite 免費層；改為在管理頁可選擇 Claude 的模型（例如日常對話用較便宜的模型，需要更強推理時可切換），並顯示目前預估花費。
- **資料庫／託管**：優先維持 Supabase 免費方案（沿用 v1 3.3 節額度資訊），接受一週無活動會暫停的限制；若之後預算允許，可升級 Supabase Pro（約 US$25/月起）換取不暫停與正式備份，屬於「保留但非第一階段必做」的選項。
- **權限（RLS）**：沿用 v1 第 8 章的技術做法（Supabase RLS、service_role 只在後端），但**資料表與政策的複雜度可以先做「單一擁有者可讀寫自己房間」的簡化版**，不必一次做滿 owner/admin/member/viewer 四級全部情境的測試矩陣。

## 5. 資料庫調整重點（相對 v1 第 7 章）

- `agents` 表的語意調整：MVP 階段的 `agent` 記錄對應「供應商」而非「角色」，例如 `slug = claude` / `gpt` / `gemini`，`system_prompt` 可以很簡短（甚至留空，先不做角色人設）。「主管代理」可以就是 `slug = claude` 這筆記錄搭配「未被點名時的預設路由」邏輯，不需要額外一張表。
- `approval_requests`／人工確認機制：只在 `tool_name` 屬於高風險（如 `file.delete`、批次修改）時才建立；`note.create`、`task.create` 等低風險工具**跳過** approval 流程、直接寫入並記一筆 `audit_logs`。
- `file_text_chunks`（v1 原本標示「第二階段才做」）：**在 v2 提前到 MVP**，因為「檔案作為多供應商共享上下文」是使用者 Q10 確認的優先需求。
- 相簿（`files` 表中 MIME 類型為圖片的子集）與 `calendar_events` 表：v2 第一階段可以不建表，之後真的要做再加，不影響既有資料結構。

## 6. 待確認／下一步（尚未在訪談中決定，建議後續處理）

1. **OpenAI、Google 的 API key 尚未申請** —— 何時要開始接 GPT／Gemini？是現在就一起申請帳號＋計費設定，還是先把 Claude 單供應商版本做完、實際用過之後再擴充？
2. **典型問題領域**——平常丟給多個 AI 互相補位的問題主要是寫程式、寫作、研究分析還是其他？這會影響「檔案夾共享上下文」該優先支援哪些檔案格式（例如程式碼 vs. 一般文件）。
3. **每週可投入時間**——決定實際開發節奏；v1 估計完整規劃需 31–52 個工作天，v2 範圍已明顯收斂（拿掉角色代理、精簡權限、拿掉相簿/行事曆、拿掉自動仲裁），但仍需要抓一個實際時間預算，才能排出階段順序。
4. 是否現在就要開始實作，還是先看過這份 v2 規劃有沒有要再調整的地方？

### 6.1 上線後發現、已記錄但先不做的項目

實作並上線 MVP 後，聊天室資料庫使用上發現以下幾點，目前判斷都不影響 MVP 堪用，先記錄下來，等之後真的需要再處理：

- **對話歷史摘要記憶**：目前 `agent-run` 每次只讀最近 24 則訊息當上下文，不會把整個歷史對話都送給 Claude，token 費用不會隨資料庫總量無限增加；但房間用得夠久之後，AI 會漸漸「忘記」更早之前的討論。**設計已定案**（尚未實作），見 `brainstorms/2026-09-18-conversation-memory-design.md`：超過 50 則訊息時，代理回覆前先把舊訊息摘要、併入既有摘要（不刪除原始訊息），之後 AI 上下文改用「摘要＋最近 24 則」；摘要在右側新增獨立分頁可查看/編輯；「刪除舊訊息」是另一個獨立開關，不隨摘要自動觸發。
- **封存聊天室／永久刪除**：`messages` 目前只會一直累積，沒有任何清除機制（訪客登出、清瀏覽器都不會刪除資料庫裡的資料，只是那個訪客帳號回不去了）。之後可以加「封存房間」「永久刪除房間」這類使用者主動觸發的功能，不要讓系統自己決定刪什麼。
- 這兩項都屬於「資料庫容量」與「長期記憶品質」的優化，MVP 現階段資料量不會立即造成問題。

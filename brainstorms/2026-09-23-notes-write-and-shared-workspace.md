# AI 寫回記事本／待辦 + 跨聊天室共用工作區：腦力激盪／探索紀錄
日期：2026-09-23 · 目標：把使用者回報的兩個功能缺口（bug #4、#5）談成可以直接實作的設計
狀態：完成
背景來源：
- brainstorms/2026-09-22-sidebar-resize-ai-context.md（notes/tasks/files 目前用 room_id 隔開、buildWorkspaceContext 只讀不寫的既有設計）
- brainstorms/2026-09-18-agentic-sandbox-workers.md（worker-task-start／consult_other_ai 自訂工具的既有模式）

## 摘要／重要決策
- notes/tasks/files 改成「完全共用」：取消 room_id 隔離，同一個使用者帳號底下的所有房間共用同一份資料。不做「房間專屬 + 共用並存」的雙軌模式。
- 既有資料遷移：room_id 改成 owner_id（依房間建立者），舊資料全部合併進同一份列表，但額外保留一個不影響查詢邏輯的「來源房間名稱」欄位，方便之後追溯。

## 問答紀錄

### Q1：共用範圍
- 問題：先談「共用範圍」（bug #5）。目前 notes/tasks/files 都用 room_id 隔開，每個房間目前實際上只有你自己一個成員（room_members 雖然支援多人協作，但前端沒有邀請成員的功能）。所以「跨聊天室共用」實際上等於「同一個使用者帳號底下的所有房間共用一份」。要採用哪種共用範圍？
- 已記錄：採用「完全共用」（推薦選項）——取消 room_id 隔離，同一使用者的所有房間都讀寫同一份 notes/tasks/files，不做房間專屬/共用並存的雙軌模式。

### Q2：既有資料處理
- 問題：既有資料要怎麼處理？目前 rooms 表有 created_by，可以直接把 notes/tasks/files 的 room_id 改成 owner_id（依房間建立者對應），之後同一使用者在不同房間建立的資料就會自然合併成一列。這樣改後，舊資料不會消失，只是全部混在同一列裡，也沒有任何標註說明原本來自哪個房間。這樣可以嗎，還是你希望保留一些來源資訊？
- 已記錄：合併但保留來源房間名稱——遷移時把原本的 room_id 對應的房間名稱抄一份存進新增的欄位（例如 `origin_room_name`），純粹作為顯示用的追溯資訊，不影響「完全共用」的查詢/RLS 邏輯（新查詢一律用 owner_id，不再篩 room_id）。

### Q3：來源房間名稱要不要顯示在畫面上
- 問題：既然要保留「來源房間名稱」，前端要不要把它顯示出來（例如每筆記事/待辦/檔案旁邊加一個小標籤顯示「來自：OO房間」）？
- 已記錄：顯示小標籤（推薦）——每筆資料旁邊顯示灰色小標籤標示原本建立於哪個房間；新建立的資料（完全共用後）不會有這個標籤，因為已經沒有房間歸屬的概念了。

### Q4：寫回記事本/待辦的適用範圍
- 問題：接下來談 bug #4（AI 寫回記事本/待辦）。目前「任務 vs 問題」分類只有 Claude（Anthropic）代理會做，GPT/Gemini 一律當問題處理。「寫回記事本/待辦」這個能力要三家供應商都能用，還是跟現在任務分類一樣只限 Claude？
- 已記錄：三家都能用（推薦）——不管跟哪一位 AI 說話，都能請它幫忙記事/加待辦。代表 agent-run 要依供應商各自跑一次「這則訊息是不是要記事/加待辦」的意圖判斷，不能只靠現有只限 Claude 的任務分類機制。

### Q5：判斷到寫入意圖後的回覆方式
- 問題：當 AI 判斷該次訊息是「寫回記事本/待辦」意圖時，回覆要怎麼表現？
- 已記錄：只回短確認（推薦）——寫入記事本/待辦後，AI 只回一句短確認（例如「已幫你記下 55」），不另外生成一段完整聊天回覆。不採用「確認 + 仍正常聊天回覆」（會多一次 API 呼叫、速度較慢）。

### Q6：記事本 vs 待辦，寫入哪一張表由誰決定
- 問題：記事本跟待辦是兩張不同的資料表（notes 有 title/content，tasks 有 title/status）。AI 判斷寫入意圖時，要怎麼決定寫進哪一張表？
- 已記錄：讓 AI 自己判斷（推薦）——分類 prompt 直接讓 AI 根據語意自行決定是「記事」還是「待辦」（例如「幫我記下...」→ notes；「提醒我/待辦是...」→ tasks），不需要使用者自己指定。

### Q7：GPT/Gemini 是否新增一次分類 API 呼叫
- 問題：目前 GPT/Gemini 每次回覆都是直接生成回覆，沒有額外的分類步驟（只有 Claude 會先跑一次「任務 vs 問題」分類）。現在要讓三家都能寫回記事本，就需要給 GPT/Gemini 也加上一次輕量分類呼叫（判斷是不是要寫入），每則訊息都會多一次 API 呼叫、多一點延遲。這個取捨可以接受嗎？
- 已記錄：可以，接受多一次呼叫的延遲（推薦）——GPT/Gemini 也比照 Claude，在正式生成回覆前先跑一次輕量分類（question / workspace_write），不採用關鍵字/正規表達式的粗略判斷方案（準確度太低）。

### Q8：功能範圍——只新增，還是也要支援修改/完成現有項目
- 問題：這次實作的範圍要包到哪裡？例如使用者說「把待辦裡的 XX 標記完成」或「把那筆記事改成 YY」，這樣的「修改/完成現有記事/待辦」要一起做嗎？
- 已記錄：新增 + 修改/完成現有項目都要支援（使用者明確選擇較大範圍，不是推薦選項）。代表分類/寫入機制要能：(a) 新增記事/待辦，(b) 依語意在既有記事/待辦裡找到對應項目並修改內容或標記完成／狀態變更。範圍擴大，需要接著談配對機制與模糊比對風險（見 Q9）。

### Q9：模糊配對（找不到/不確定要改哪一筆）的處理方式
- 問題：要讓 AI 能修改/完成現有項目，分類呼叫就需要看得到目前的記事/待辦清單（包含 id）才能指定要改哪一筆。如果 AI 找不到對應項目，或有多筆名稱相似、不確定指哪一筆，這時候要怎麼處理？
- 已記錄：不確定就直接確認問清楚（推薦）——找不到或有多筆疑似對象時，AI 不用猜，直接回覆請使用者說清楚是哪一筆，不會真的寫入/修改任何資料。分類呼叫因此需要能看到目前記事本/待辦清單（含 id），才能判斷「找到唯一對應」「找不到」「多筆疑似」三種情況。

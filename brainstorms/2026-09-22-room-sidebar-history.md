# 左側聊天室歷史清單：腦力激盪／探索紀錄
日期：2026-09-22 · 目標：設計「左側欄位歷史對話聊天室清單」功能，含新增、關閉、刪除聊天室，問清楚需求再動手
狀態：進行中
背景來源：
- `src/features/rooms/RoomGate.tsx`、`src/features/rooms/useRooms.ts`：目前完全沒有房間清單 UI，登入後沒有房間就自動建一間「我的協作室」，有房間就直接進第一間，使用者從來沒看過房間列表

## 問答紀錄

### Q1：「關閉聊天室」具體是什麼意思？
- 問題：(a) 封存／隱藏（建議）——資料都還在，只是從左側清單移到「已封存」區或直接隱藏，之後可以找回來、重新打開繼續聊 (b) 跟「刪除」是同一件事，只是 UI 用詞不同 (c) 只是關掉視窗／取消選取，不做任何資料庫變更，純前端狀態
- 已記錄：使用者選 **(a) 封存／隱藏**。
- 影響：「關閉」跟「刪除」是兩個不同的資料狀態，不是同一個動作的兩種說法。這代表 `rooms` 表需要一個狀態欄位（例如 `status` 或 `archived_at`）來區分「使用中」跟「已封存」，光靠現有的 `rooms_delete_owner` 這條硬刪除政策不夠用——刪除還是刪除，但「關閉」不能真的把資料庫那筆砍掉。

### Q2：已封存的聊天室，在左側清單要怎麼顯示？
- 問題：(a) 清單最下方有一個可展開的「已封存」區塊（建議） (b) 完全從主清單消失，另外一個入口查看
- 已記錄：使用者沒有直接選 a/b，回答「整體左側欄位顯示如同 https://claude.ai/new 一樣」——指的是希望**整體左側欄位的視覺／互動風格**比照 Claude.ai 的對話清單：扁平的時間排序列表、每一列 hover 才顯示操作圖示（例如刪除/更多選單）、上方有明顯的「+ 新對話」按鈕、目前開啟的聊天室要有醒目的選中樣式。
- 待釐清：Claude.ai 的側欄預設沒有把「封存」當成使用者看得到的分區概念（它主要就是刪除 + 一個扁平清單）。使用者是否也是這個意思——封存的聊天室**直接從清單消失、不需要另外顯示一個「已封存」區塊**，只是單純不列出來？還是使用者只是想沿用視覺風格，封存清單本身還是想要 Q2 選項 a 那種「可展開找回來」的設計？→ 待下一題釐清

### Q2.1：已封存的聊天室，需要在左側清單上有一個找回來的入口嗎？
- 問題：(a) 需要可展開的已封存區塊（建議） (b) 封存後直接消失，之後需要的話再另外設計
- 已記錄：使用者選 **(a) 需要可展開的已封存區塊**。
- 影響：確定 Q2 的設計——左側整體視覺／互動風格比照 Claude.ai（扁平清單、hover 顯示操作、「+ 新對話」按鈕、選中樣式），但清單最下方仍保留一個可展開的「已封存」區塊，封存的聊天室收在裡面、點開就能找到並重新打開繼續聊。

### Q3：刪除聊天室需要二次確認嗎？
- 問題：(a) 需要確認對話框（建議）——符合這個專案一貫原則（難復原才需要確認） (b) 不需要，點一下就直接刪
- 已記錄：使用者選 **(a) 需要確認對話框**。
- 影響：刪除按鈕要接一個確認對話框（「確定要永久刪除這間聊天室嗎？」），確認後才真的送出刪除請求；「關閉（封存）」因為可以找回來，不需要這個確認流程，維持點一下就直接封存。

### Q4：點「＋ 新對話」建立新聊天室時，名稱怎麼決定？
- 問題：(a) 先跳出小視窗輸入名稱 (b) 直接建立、用預設名稱，之後可以改 (c) 自動用第一則訊息內容當標題（像 Claude.ai）
- 已記錄：使用者選 **(c) 自動用第一則訊息內容當標題**。
- 追問細節：「用第一則訊息當標題」具體怎麼做？(i) 直接截取訊息文字當標題（簡單，不額外花費） (ii) 呼叫 AI 產生精簡摘要標題（像 Claude.ai 真正的做法）
- 已記錄：使用者選 **(ii) 呼叫 AI 產生精簡摘要標題**，範例：使用者輸入「幫我看看這段 Python code 為什麼會報錯，這是我寫的排序演算法…」，AI 產生標題「排序演算法 debug」。
- 影響：
  - 點「＋ 新對話」要立刻建立一間房間（預設名稱例如「新對話」）並直接進入，不用先跳輸入框；
  - 使用者送出第一則訊息後，非同步另外呼叫一次 AI（小額度、快速模型）產生精簡標題，完成後更新這間房間的 `name`，不能拖慢原本聊天室的正常回覆流程；
  - 需要新增一個機制記錄「這間房間的標題是否已經產生過」，避免每次都重新命名（例如生成過一次之後就不再觸發，即使之後又有新訊息）。

### Q5：左側清單排序方式，要不要按時間分組？
- 問題：(a) 按最新活動時間排序，不分組（建議） (b) 按時間區塊分組（今天/過去 7 天…）
- 已記錄：使用者選 **(a) 按最新活動時間排序，不分組**。
- 影響：清單依「最後活動時間」（新訊息時間，不是建立時間）由新到舊排序；需要知道每間房間「最後一則訊息的時間」，現有 `useRooms()` 目前只是單純 `select * order by created_at`，之後要改成能反映最新活動時間排序（可能要在 `rooms` 表加一個 `last_message_at` 欄位、或查詢時 join messages 表取最大值，實作時再決定用哪種方式）。目前也不需要做「今天/過去 7 天」這種分組 UI。

### Q6：手機尺寸上，左側歷史清單要放哪裡？
- 問題：(a) 滑出式抽屜（建議）——左上角漢堡圖示點開，選完自動收起 (b) 變成第三個切換頁籤，跟現有「聊天/工作區」並列
- 已記錄：使用者選 **(a) 滑出式抽屜**。
- 影響：`RoomPage.tsx` 的 header 要加一個漢堡選單按鈕（手機才顯示），點開後從左邊滑出歷史清單，選取房間或做新增/關閉/刪除動作後自動收起；桌面版則是常駐在畫面左側，不需要開關。

### Q7：要不要加手動重新命名功能？
- 問題：(a) 要，加一個重命名功能（建議） (b) 不用，這次先不做
- 已記錄：使用者選 **(a) 要**。
- 影響：範圍多一個小功能——清單每一列 hover 時的操作選單，除了「關閉」「刪除」，還要加「重新命名」，點了之後可以直接編輯名稱（沿用現有 `rooms_update_owner` RLS 政策即可，不需要新政策）。

### Q8：登入後要自動進入最近的房間，還是顯示空白歡迎頁？
- 問題：(a) 保留現有行為，自動進最近活動的房間（建議） (b) 改成空白歡迎頁／選擇頁，使用者自己從清單選
- 已記錄：使用者選 **(b) 改成顯示空白歡迎頁／選擇頁**——不採納建議選項。
- 影響：`RoomGate.tsx` 現有「沒房間就自動建一間、有房間就直接導向第一間」的邏輯要整個換掉，`/` 這個路徑不再自動轉址到某間房間，而是顯示一個類似 Claude.ai 首頁的空白歡迎狀態（左側維持房間清單，右側／中間是歡迎畫面 + 也許一個「開始新對話」按鈕），由使用者自己點選或新增。
- 待釐清：全新使用者（一間房間都沒有）第一次登入，也是先看到空白歡迎頁、自己按「＋新對話」才建立第一間；還是完全新帳號這個特殊情況仍然保留「自動建一間」的行為，只有「已經有房間但沒選」的情況才顯示歡迎頁？→ 待下一題釐清

### Q8.1：完全新帳號第一次登入，也是空白歡迎頁嗎？
- 問題：(a) 也看空白歡迎頁，自己點新增（建議） (b) 保留自動建立第一間的行為
- 已記錄：使用者選 **(a) 也看空白歡迎頁，自己點新增**。
- 影響：行為完全統一，不用分「全新帳號」跟「已有房間但沒選」兩種情況——`RoomGate.tsx` 的自動建立邏輯整個移除，不管有沒有房間，登入後一律顯示空白歡迎頁，由使用者自己按「＋新對話」開始。這也代表原本「沒有房間清單選擇畫面」的 MVP 設計（訪談 Q7：使用範圍主要自己一個人用）正式被這次的多房間歷史清單取代。

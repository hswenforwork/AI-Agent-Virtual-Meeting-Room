# GPT 專案審查後續：5 個確認屬實的問題該怎麼修
日期：2026-09-23 · 目標：把使用者請 GPT 審查、經我逐一 verify 確認屬實的 5 個問題談成可以直接實作的設計
狀態：完成
背景來源：
- 這次對話裡我對 5 個問題的逐項驗證結果（room_id cascade delete、chat-dispatch 序列執行、
  useAgentRunStatus 沒有初始查詢、messages/history 上限、file-register 文字擷取範圍）
- brainstorms/2026-09-23-notes-write-and-shared-workspace.md（上次把 notes/tasks/files 改成
  跨房間共用的設計，問題 #1 是這次改動遺留的坑）
- docs/MVP規劃-v2.md（「平行比較」「各自獨立回答、不互相看到彼此答案」的原始設計承諾，
  問題 #2 是目前實作跟這份文件不符的地方）

## 摘要／重要決策
- **#1 刪房間連帶刪共用資料**：notes/tasks/files 新增 owner_id 欄位徹底解耦，真正歸屬使用者；
  room_id 降級為「來源房間」參考欄位（on delete set null，不再 cascade）。
- **#2 平行點名/非真正協作**：
  - chat-dispatch 的 for-await 序列迴圈改成 Promise.all 平行觸發所有被點名的代理。
  - agent-run 組歷史訊息時排除「回覆同一則觸發訊息的其他代理回覆」，結構性保證獨立、不依賴時間差。
  - 額外納入「代理互相協作」：用三家供應商真正的 AI tool use（不是輕量分類呼叫），所有回覆
    （不分有沒有被使用者明確點名）只要沒超過接力上限都帶 loop-in 工具定義；同一則觸發訊息最多
    一次接力（A 可拉 B，B 不能再拉 C）；B 的回答獨立顯示成一則新訊息，A 不做二次整合；自動執行
    不需使用者確認；B 沒 key 的供應商不會出現在可選清單。
- **#3 監控資訊不足**：`useAgentRunStatus` 掛載時先 select 一次現有 queued/running 的
  `agent_runs`，再接上既有 Realtime 訂閱，跟 `useMessages` 的「先查再訂閱」模式一致。
- **#4 資料庫負擔／舊對話不易查閱**：
  - 畫面端：加上往上捲動載入更舊訊息的分頁功能。
  - AI 記憶端：加自動摘要機制，房間層級（非使用者層級），累積超過 20 則未摘要訊息就折進摘要；
    UI 加一個查看入口（WorkspaceTabs 第 4 個分頁「對話摘要」）。
- **#5 PDF/DOCX/XLSX 不擷取內容**：PDF 用三家供應商各自的原生文件輸入（Anthropic document
  content block／OpenAI 對應檔案輸入／Google Gemini 檔案輸入），不再共用「純文字塞進 system
  prompt」邏輯，三個 provider adapter 的請求組裝方式都要改；DOCX/XLSX 用 mammoth/xlsx 等解析庫
  在 file-register 就地擷取成純文字，沿用既有 file_text_chunks 架構。
- **實作順序**：5 個問題一次全部做完，最後一起驗證、一起上線，不分批 PR。

## 問答紀錄

### Q1：#1 刪除房間連帶刪掉共用資料的修法方向
- 問題：根本原因是 notes/tasks/files 仍用 room_id 當外鍵，只是 RLS 放寬成「同一使用者的所有房間都看得到」，資料本身仍掛在某個具體房間下、跟著房間一起被 cascade 刪除。最徹底的修法是新增 owner_id 欄位（直接指向使用者）當真正歸屬，room_id 改成只是「來源房間」的參考欄位（on delete set null，不再 cascade）——之後刪除任何房間都不會碰到共用資料，只是那筆資料的「來源房間小標籤」會變空白。這個方向可以嗎？
- 已記錄：新增 owner_id，徹底解耦（推薦）。

### Q2：#2 修法方向——平行發送 + 歷史訊息排除同批次其他代理回覆
- 問題：根本問題有兩個：(a) chat-dispatch 依序等待每一位代理回完才觸發下一位，(b) 因此後面的代理會讀到前面已完成的回覆，跟文件承諾的「各自獨立回答、平行並排顯示、不互相看到彼此答案」不符。提出兩個修正：1) chat-dispatch 改成平行發送給所有被點名的代理（不再依序等待，三家供應商的 RPM 限制本來就是分開算的）；2) agent-run 組歷史訊息時，明確排除「回覆同一則觸發訊息的其他代理回覆」，不再依賴執行順序/時間差，保證真正獨立。這兩項可以嗎？
- 已記錄：兩項都改（推薦）——1) chat-dispatch 的 for-await 序列迴圈改成 Promise.all 平行觸發；2) agent-run 的歷史查詢加上排除「reply_to_id = 這次觸發訊息 id」的其他代理回覆，用結構性過濾保證獨立，不依賴執行時間差。

### Q3：代理互相協作是否納入這次範圍、用什麼機制
- 問題：#2 標題提到的「代理互相協作」（回覆會不會再點名另一位代理）是比獨立平行修正更大的新功能，這次要一起設計嗎？
- 已記錄：現在一起設計代理互相點名（使用者明確選擇較大範圍，不是推薦選項）。

### Q4：點名機制——輕量分類呼叫 vs. 真正的 AI tool use
- 問題：機制上可以沿用「寫回記事本」用過的輕量分類呼叫模式（回覆生成完後再跑一次判斷要不要拉別的代理），或是用三家供應商真正的 tool use（模型生成回覆時能主動呼叫工具），後者原生但要分別實作三家供應商的 tool use 格式，工程量大得多。要選哪個？
- 已記錄：用真正的 AI tool use（使用者明確選擇較大範圍，不是推薦選項）。三家供應商（Anthropic/OpenAI/Google）的 generate()/generateStream() 都要能接受 tool 定義、處理 tool_use/function_call 這個 stop reason。

### Q5：協作結果呈現方式
- 問題：代理 A 用 tool use 拉入代理 B 後，得到 B 的回答，接下來要怎麼顯示給使用者？
- 已記錄：B 的答案單獨顯示成一則新訊息（不是推薦選項）。代表 A 呼叫工具後不需要再把 B 的答案回傳給 A 做二次整合——A 的回覆到「呼叫工具」這個動作為止（連同 A 當下已經產生的文字，例如「這個我建議問問 Gemini」），B 的回答是完全獨立的新一則代理訊息，不需要對 A 做第二次 API 呼叫把 tool_result 餵回去。

### Q6：接力深度上限
- 問題：防止無限循環（A 拉 B、B 又拉回 A…）與控制成本，需要設一個接力深度上限。最簡單的做法是：同一則使用者訊息最多只允許拉一次——第一位回覆的代理（A）可以拉入另一位（B），但 B 的回答本身不再給 tool、不能再拉第三位。這樣可以嗎？
- 已記錄：最多一次接力（推薦）。同一則觸發訊息最多只有一次 loop-in；被拉入的代理（B）產生回覆時不附帶 loop-in 工具定義。

### Q7：loop-in 工具的適用範圍
- 問題：哪些回覆會有「拉入另一位代理」的 tool？不管是沒點名的預設主管代理回覆，還是使用者明確 @點名某一位代理，只要是第一輪回覆（沒超過接力上限），都會帶 loop-in 工具定義嗎？
- 已記錄：所有回覆都有（推薦）。不分是否為使用者明確點名，只要沒超過 Q6 的接力上限，生成回覆時都附帶 loop-in 工具定義，由代理自己判斷要不要用。

### Q8：拉入另一位代理要不要先確認
- 問題：代理決定拉入另一位後，要不要先讓使用者確認才執行還是自動執行？這會消耗另一家供應商的 API 額度（但用的是使用者自己的金鑰，跟上次「寫回記事本」一樣自動寫入不需要確認）。
- 已記錄：自動執行，不需確認（推薦）。

### Q9（無需詢問，直接採用）：#3 修法
- 沒有其他合理選項，直接採用：`useAgentRunStatus` 掛載時先 `select` 一次目前房間還在 queued/running 的 `agent_runs`，再接上既有 Realtime 訂閱持續更新，跟 `useMessages` 現有的「先查再訂閱」模式一致。

### Q10：#4 畫面端——要不要加上往上捲動載入更舊訊息
- 問題：目前聊天畫面固定只抓「最新 200 則」，超過就永遠看不到更舊的。要不要加上「往上捲動載入更舊訊息」的分頁功能？
- 已記錄：加上往上捲動載入更舊訊息（推薦）。畫面先顯示最新 200 則，使用者往上捲到頂部時再向後端拉下一頁更舊的訊息。

### Q11：#4 AI 記憶端——要不要做自動摘要機制
- 問題：目前 agent-run 組歷史訊息時只抓最近 24 則，更舊的對話 AI 完全不知道。要不要加上自動摘要機制（舊訊息滾出去前先用 AI 摘要成一段摘要，之後組歷史時把摘要一起插進 system prompt）？
- 已記錄：現在一起設計自動摘要機制（使用者明確選擇較大範圍，不是推薦選項）。摘要是房間層級（chat 訊息歷史本身沒有變成跨房間共用，只有 notes/tasks/files 才有），不是使用者層級。

### Q12：自動摘要觸發時機
- 問題：每次 agent-run 組歷史訊息時，如果發現「已摘要範圍」與「最新 24 則」之間累積了超過門檻（例如 20 則）的未摘要訊息，就先折進摘要再繼續正常回覆。這樣每則訊息都會被摘要到，但會多一次 API 呼叫成本。可以嗎？
- 已記錄：累積超過門檻就折進摘要（推薦）。門檻先訂 20 則未摘要訊息。

### Q13：摘要要不要讓使用者看得到
- 問題：自動摘要的內容要不要讓使用者看得到，還是後台內部用就好？
- 已記錄：現在就加一個可以查看摘要的入口（不是推薦選項）。放置位置工程面決定：在 WorkspaceTabs 加第 4 個分頁「對話摘要」，跟記事本/待辦/檔案夾同一排，最符合現有 UI 慣例。

### Q14：#5 PDF 擷取方式
- 問題：要支援 PDF，是用解析庫本地擷取文字（沿用 file_text_chunks 既有架構），還是直接把文件交給 Anthropic Messages API 原生理解 PDF（不用自己解析，但只對 Claude 有效）？
- 已記錄：直接交給 Anthropic 原生理解 PDF（不是推薦選項）。

### Q15：#5 是否要為三家供應商都做原生文件輸入整合
- 問題：Anthropic 原生 PDF 理解只對 Claude 有效，GPT/Gemini 對話中的 PDF 內容仍然看不到。要接受這個限制，還是也要為 OpenAI/Google 各自的文件輸入能力做對應整合？
- 已記錄：三家都要做對應的文件輸入整合（不是推薦選項，使用者明確要求最大範圍）。代表 PDF 的上下文注入不能再用現有「純文字塞進 system prompt」的共用邏輯，三家供應商各自要有自己的「原生文件輸入」串接方式：
  - Anthropic：Messages API 的 document content block（base64 PDF）
  - OpenAI：對應的檔案/文件輸入方式
  - Google：Gemini API 的檔案/文件輸入方式
  這是這次 5 個問題裡工程量最大的一項，需要重新設計 generate()/generateStream() 的請求組裝方式（從純文字訊息陣列，改成能附加文件內容的訊息格式），三個 provider adapter 都要改。

### Q16：DOCX/XLSX 擷取方式
- 問題：三家供應商的原生文件輸入通常只支援 PDF（跟圖片），不會直接解析 DOCX/XLSX 這種 Office 二進位格式。DOCX/XLSX 要怎麼處理？
- 已記錄：DOCX/XLSX 用解析庫本地擷取文字（推薦）。PDF 走三家原生文件輸入（Q15），DOCX/XLSX 用 mammoth/xlsx 這類庫在 file-register 就地擷成純文字，沿用現有 file_text_chunks 架構，三家供應商都用得到。

### Q17：實作順序
- 問題：範圍比一開始想的大很多，實作上想怎麼排？
- 已記錄：一次全部做完再一起交（不是推薦選項，使用者明確要求）。5 個問題都在同一批實作完成，最後一起驗證、一起上線，不分批 PR。

## 待釐清事項
- B（被拉入的代理）沒有設定 API key 時怎麼辦 → 工程面決定：loop-in 工具定義只列出使用者「有設定 key」的其他供應商，沒有 key 的供應商不會出現在可選清單裡，不需要另外詢問使用者。
- B 產生回覆時能看到多少上下文 → 工程面決定：跟一般回覆一樣的完整歷史（同一份 shared workspace 邏輯），額外加上 A 附帶的理由/問題當作提示，不需要另外詢問使用者。
- 三家供應商各自「原生文件輸入」的確切 API 格式（Anthropic document content block 已知；OpenAI、Google 的確切欄位格式）→ 實作前需要各自查證最新文件，不用另外詢問使用者。

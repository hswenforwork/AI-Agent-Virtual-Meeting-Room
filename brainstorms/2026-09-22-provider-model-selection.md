# AI 供應商模型選擇清單：腦力激盪／探索紀錄
日期：2026-09-22 · 目標：讓使用者能在「設定」頁快速挑選每個供應商要用哪個模型，不用再靠後端寫死的預設值
狀態：進行中
背景來源：
- 目前架構：模型完全由後端 Edge Function 的環境變數決定——`DEFAULT_CLAUDE_MODEL`／`DEFAULT_GPT_MODEL`／`DEFAULT_GEMINI_MODEL`，使用者在前端完全看不到、也不能選
- `agents` 表其實已經有一個 `model_config jsonb not null default '{}'::jsonb` 欄位（`supabase/migrations/0001_init.sql`），`agent-run` 也已經會讀 `agent.model_config.model` 優先於環境變數預設值——但目前完全沒有任何 UI 寫入這個欄位，所以永遠是空的，永遠退回環境變數預設值
- 今天才剛修好一個真實 bug：Gemini 的預設模型 `gemini-2.5-flash` 已經被 Google 淘汰、寫死的字串過期導致 API 404，改成 `gemini-3.8-flash` 才修好。使用者看到這個 bug 之後提出這個功能構想
- BYOK（`brainstorms/2026-09-22-user-api-key-settings.md`）已經讓金鑰變成「每個使用者、每個供應商各自一把」，不再是房間層級或部署者層級的設定

## 使用者原話
「AI API Key因該要有各供應商最新模型選擇清單，以便使用找快速套用模型。」

## 摘要／重要決策
（隨訪談持續更新）

## 問答紀錄

### Q1：模型選擇要套用在哪個層級？
- 問題：(a) 跟金鑰綁在一起，使用者層級（建議） (b) 房間層級，沿用現有的 `agents.model_config` (c) 兩者都要——使用者層級設預設模型，房間層級可以覆蓋
- 已記錄：使用者選 **(c) 兩者都要**。
- 影響：複雜度變高，需要兩層資料：
  1. 使用者層級的預設模型選擇（跟 BYOK 金鑰一樣，存在使用者、供應商維度）
  2. 房間層級的覆蓋（沿用既有的 `agents.model_config` 欄位，目前有欄位但沒有 UI）
  `agent-run` 目前解析模型的順序是 `agent.model_config.model ?? DEFAULT_MODEL_BY_PROVIDER[provider]`（寫死的環境變數預設值）；這次要改成三層優先順序：房間覆蓋 → 使用者預設 → 寫死的環境變數兜底（避免使用者完全沒設定時整個掛掉）。
  前端也要有兩個 UI 入口：「設定」頁的使用者層級預設模型選擇，跟房間內某個地方（待下一題確認位置）的房間層級覆蓋選擇。

### Q2：模型清單的內容怎麼來？
- 問題：(a) 即時呼叫供應商自己的模型清單 API（建議） (b) 我維護一份精選清單，寫進程式碼 (c) 兩者都要，即時清單為主、精選清單當備援
- 已記錄：使用者選 **(a) 即時呼叫供應商自己的模型清單 API**。
- 影響：不會再有「寫死的模型名稱過期」這類問題（今天才修的 `gemini-2.5-flash` bug 從根本上不會再發生），但幾件事要處理：
  - 三家供應商都各自有「列出可用模型」的端點，但都需要帶著使用者自己的 API key 才能呼叫（不能匿名列出）——代表清單只能在使用者已經輸入金鑰之後才抓得到，抓取時機待後續問題釐清
  - 供應商回傳的原始清單通常很雜（包含 embedding、audio、image 專用模型、舊版 snapshot 等），需要過濾成「聊天用、看起來合理」的子集，過濾規則要另外設計（例如 Anthropic 用 `type` 或名稱前綴判斷、OpenAI／Google 同理）——這部分待實作時查證各家目前 `/models` 端點實際回傳的欄位
  - 使用者選了 (a) 沒選 (c)，代表**不需要**額外維護一份程式碼內的精選清單當備援；如果即時呼叫失敗，UI 上怎麼處理待後續問題確認（例如退回手動輸入 model id 字串）

### Q3：模型清單什麼時候抓取？
- 問題：(a) 金鑰測試通過、儲存成功後自動抓一次，存起來（建議） (b) 每次打開「設定」頁都即時重抓
- 已記錄：使用者選 **(a) 金鑰測試通過、儲存成功後自動抓一次，存起來**。
- 影響：
  - `save-api-key` 這個 Edge Function 在金鑰測試通過、寫進 Vault 成功之後，要多一步：呼叫該供應商的模型清單端點，把結果存起來（存在哪張表／欄位待實作時設計，可能是 `user_provider_keys` 新增一個 `cached_models jsonb` 欄位，或另開一張表）
  - 因為是「存起來」不是「即時抓」，清單會有暫時性的過時風險（供應商出新模型，使用者不會自動看到，除非重新觸發抓取）——需要一個「重新整理清單」的手動按鈕，待後續問題確認要不要做、放在哪裡
  - 抓取失敗（例如清單 API 剛好逾時）時的行為待後續問題確認：金鑰本身已經測試通過了，不應該讓儲存整個失敗，比較合理是金鑰照常存、清單抓取失敗就記錄空清單或錯誤狀態，之後可以重試

### Q4：需要「重新整理清單」的手動按鈕嗎？
- 問題：(a) 要，在「設定」頁每個供應商旁邊加一個小按鈕（建議） (b) 不需要，要更新就重新存一次金鑰
- 已記錄：使用者選 **(a) 要，加一個手動重新整理按鈕**。
- 影響：`ProviderKeyCard` 這個既有元件要多一個「重新整理模型清單」的按鈕跟對應的 loading／錯誤狀態；後端需要一個新的 Edge Function（或擴充現有的），單獨負責「用已經存好的金鑰重抓模型清單」，不需要使用者重新輸入金鑰本身（服務端已經可以用 `get_user_provider_key` 讀出明碼金鑰來呼叫供應商）。這個按鈕同時也是 Q3 提到的「抓取失敗時的重試手段」。

### Q5：房間層級的模型覆蓋要放在房間裡的哪裡？
- 問題：(a) 房間內新增一個「代理設定」面板（建議） (b) 這次先不做房間層級 UI，只做使用者層級
- 已記錄：使用者選 **(b) 這次先不做房間層級 UI，只做使用者層級**。
- 影響：**這次實作範圍縮小為只做使用者層級**（Q1 選的「兩者都要」，這次先做完使用者層級那一半）。`agents.model_config` 欄位跟 `agent-run` 讀取它的邏輯維持現狀（存在但沒有 UI 寫入，一律是空的），房間層級覆蓋 UI 留到之後單獨開一輪訪談／實作。

### Q6：房間層級的覆蓋權限（先記錄下來，等之後真的做房間層級 UI 時直接沿用，這次不影響實作範圍）
- 問題：房間層級的覆蓋，房間內任何成員都能改，還是只有房間擁有者（owner_id）？
- 已記錄：使用者選 **只有房間擁有者**。
- 影響：等之後做房間層級 UI 時，寫入 `agents.model_config` 的 RLS／Edge Function 權限檢查要比照房間擁有者專屬操作的既有模式（例如房間刪除、封存）。這次不用實作，先記錄決策。

### Q7：使用者還沒手動選模型時，套用哪一個？
- 問題：(a) 自動選清單第一個 (b) 繼續用現在寫死的環境變數預設值（建議）
- 已記錄：使用者選 **(b) 繼續用現在寫死的環境變數預設值**。
- 影響：`user_provider_keys`（或新欄位）裡的「使用者選的模型」在使用者真正手動選擇之前維持 `null`；`agent-run` 的模型解析順序變成：使用者選的模型（非 null）→ 環境變數預設值（`DEFAULT_CLAUDE_MODEL`／`DEFAULT_GPT_MODEL`／`DEFAULT_GEMINI_MODEL`，跟今天修好的 bug 是同一組）。這代表環境變數預設值這幾個常數**不會被這次功能取代**，仍然要維護、仍然可能過期，只是變成「使用者沒手動選時的兜底」而不是唯一途徑。

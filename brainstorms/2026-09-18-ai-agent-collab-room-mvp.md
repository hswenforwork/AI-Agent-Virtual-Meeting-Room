# AI Agent 協作室（零成本 MVP）：腦力激盪／探索紀錄
日期：2026-09-18 · 目標：釐清使用者對「AI Agent 協作室」MVP 規劃文件的真實需求、驗證假設、找出規劃落差與風險，並確認是否/如何據此開始實作
狀態：進行中
背景來源：使用者上傳的規劃文件《AI Agent 協作室：零成本 MVP 完整規劃》（GPT 撰寫，2026-09-18 版本 1.0）

## 摘要／重要決策
- **核心動機與文件預設架構有重大落差**：使用者真正的痛點是「不同 AI 供應商（如 GPT、Claude、Gemini 等）能解決彼此解決不了的問題」，目前是手動開多個供應商的網頁互相丟問題分析。文件中的 MVP 設計是「四個角色代理（主管/研究/程式/測試）」，且明文寫「第一版可以共用同一個便宜模型（Gemini），未來再讓不同代理使用不同模型」（文件第 14、95-100 行）。這代表**文件把「多供應商」當作二期功能，但使用者的核心需求其實是多供應商本身**，需要在後續問題中釐清如何調和。
- 使用者認為這是普遍痛點，不只自己遇到（暗示可能有意做給更多人用，待 Q1 選項 c 進一步確認）。

## 問答紀錄

### Q1：驅動這個專案的核心動機是什麼？
- 問題：這份規劃相當龐大，想確認背後真正目的是 (a) 自己實際工作要用來加速任務 (b) 學習全端+AI Agent 開發 (c) 做成產品給其他人用 (d) 其他
- 已記錄：使用者原話——「因為我在使用AI開放產品時確實遇到不同ai能解決原本AI解決不了的問題，所以我希望可以在同一個聊天室內呼叫不同AI提出不同看法或解決方案，目前我都是手動開兩個不同供應商的AI互相幫忙，把修不好的問題丟給另一個AI分析，我相信這問題不止我遇到而已。」
- 解讀：核心動機接近選項 (a)，但描述的具體痛點是「多供應商模型互相補位」，而非文件預設的「角色分工代理」。使用者也暗示這可能是共通痛點（可能傾向未來做成產品，但尚未明確選 (c)）。
- 待釐清：這個專案的目標使用者最終是只有自己，還是也考慮未來給其他人用？→ 使用者本人（後續會問）

### Q2：核心能力是「多供應商」還是「角色分工」？
- 問題：文件設計是角色代理（主管/研究/程式/測試）共用同一個 Gemini 模型、多供應商是未來功能；但使用者痛點是不同供應商互相補位。詢問優先順序：(a) 多供應商優先 (b) 角色分工優先 (c) 兩者合一（角色＝供應商別名）(d) 其他
- 已記錄：使用者選 **(a) 多供應商優先**。核心是「同一問題能分別問不同供應商（GPT/Claude/Gemini/其他），拿到不同視角」；角色分工（主管/研究/程式/測試）是次要，MVP 可以先不做。
- 影響：這代表文件第 10.4 節的 Provider Adapter（原規劃為「第一版不用，未來再加」）需要提前成為 MVP 第一階段的核心，而非角色路由。點名機制（`@研究代理`）也可能要改成或並存「`@GPT` `@Claude` `@Gemini`」這種以供應商為單位的點名。

### Q3：目前手動比較的供應商是哪些？付費型態是網頁版還是 API？零成本是否為硬限制？
- 問題：確認 (a) 目前手動比較用的供應商 (b) 是付費網頁版還是有 API key (c) 若多供應商需要花錢用 API，能否接受，還是零成本是硬限制
- 已記錄：使用者原話——「目前有ChatGPT、Claude、Gemini付費訂閱網頁版，未來多供應商必須要花一點錢才能用 API我可以接受」。
  - 目前是 **ChatGPT、Claude、Gemini 三家的付費訂閱網頁版**，尚未確認是否已有對應的 API key。
  - **「零成本」不再是硬限制**：使用者明確接受未來為了多供應商 API 而花錢。
- 影響：
  1. 文件原本圍繞「零成本」（GitHub Pages + Supabase Free + Gemini 免費層）打造的整份規劃的前提假設已經鬆動，需要重新評估技術棧與模型選擇，不能只鎖 Gemini Flash-Lite 免費層。
  2. 付費網頁訂閱（ChatGPT Plus / Claude Pro / Gemini 訂閱）**不等於 API 存取權**——OpenAI、Anthropic、Google 的 API 是各自獨立計費（依 token 用量），需要另外到 OpenAI Platform / Anthropic Console / Google AI Studio 申請 API key 並綁定付款方式，這件事使用者可能還沒做。
  3. 需要進一步問清楚「一點錢」的預算範圍，才能決定要接入哪些模型（例如是否用便宜的 mini/flash 模型，還是也要接旗艦模型）。
- 待釐清：使用者是否已經有 OpenAI／Anthropic／Google 的 API key？若沒有，是否需要協助申請流程？→ 待下一題釐清

### Q4：目前有哪些 API key？每月預算？
- 問題：(a) 是否已有 OpenAI/Anthropic/Google 的 API key (b) 每月能接受的 API 費用預算數字
- 已記錄：使用者原話——「目前有Anthropic api key，每月基本預算30美金，依專案大小可提升上限」。
  - **目前只有 Anthropic（Claude）API key**，OpenAI、Google 的 API key 尚未確認持有（未提及，視為尚未申請）。
  - 每月基本預算 **US$30**，可依專案規模彈性提高上限（非硬性天花板）。
- 影響：MVP 第一步可以先用「單一供應商（Claude API）打通整條路徑（登入→聊天→呼叫 API→存回資料庫）」，再擴增 OpenAI／Gemini，而不必一開始就三家 API 同時搞定，降低起始複雜度與需要同時申請/除錯三組金鑰的風險。
- 待釐清：是否要現在協助申請 OpenAI／Google 的 API key 與計費設定，還是先用 Claude 打通 MVP 再說？→ 待後續釐清

### Q5：多供應商互相補位的實際互動方式？
- 問題：(a) 平行比較：一次點名多家，答案並排顯示 (b) 手動接力：把一家的回答轉丟給另一家 (c) 自動接力/仲裁：系統偵測失敗自動轉發或統整 (d) 先做最簡單版本再迭代
- 已記錄：使用者原話——「A，平時聊天只有主管代理回覆，只有@其他代理，那些代理才介入回覆，主管代理不回覆。」
  - 選 **(a) 平行比較**：一次點名多家供應商，各自答案並排顯示，使用者自己判斷。
  - 同時**確認並延續文件原本的點名路由邏輯**（文件 6.2 節）：沒有 `@` 時，預設由「主管代理」回覆；一旦 `@` 點名其他代理（此處＝供應商，如 GPT/Claude/Gemini），只有被點名的介入回覆，主管代理當輪不回覆。
- 解讀：這代表「主管代理」這個角色被保留下來，但性質變成「預設值班的那個供應商／助理」，而非文件原本「負責派工整合的管理角色」。
- 待釐清：**「主管代理」本身是用哪一個供應商／模型？** 是固定用目前唯一有 API key 的 Claude，還是使用者想另外設定？主管代理在其他代理被點名回答後，會不會事後做總結/仲裁，還是完全不參與該輪？→ 待下一題釐清

### Q6：主管代理是誰／用哪個模型？其他代理回答時主管代理是否參與？
- 問題：(a) 主管代理＝Claude（目前唯一有 API key 的供應商）(b) 主管代理是獨立於三家供應商外的第四角色 (c) 先用最簡單版本；另外確認其他代理回答時主管代理是否會總結/仲裁
- 已記錄：使用者原話——「C / 其他代理回答時，主管代理完全不參與」。
  - 選 **(c) 先用最簡單版本**（即等同 (a)：主管代理＝Claude，因為目前唯一有 API key）。
  - **確認**：當 `@GPT`、`@Gemini` 等其他代理被點名回答時，主管代理完全不插話、不總結、不仲裁，答案單純並排顯示。

### Q7：最終使用範圍是只有自己，還是也給其他人用？
- 問題：(a) 完全只有自己用 (b) 主要自己用，但想保留未來分享給少數朋友/同事的可能性 (c) 明確要做成產品給不特定多人用
- 已記錄：使用者選 **(b) 主要自己用，但想保留未來分享給少數朋友/同事的可能性**。
- 影響：需要保留基本帳號系統＋房間（room）概念（因為以後可能要分享），但**不需要**做到文件中企業級的角色權限（owner/admin/member/viewer 四級、精細 RLS 稽核等）。MVP 可以先做「單一使用者為中心、結構上預留多人擴充空間」的輕量版本，而不必一開始就把 8.1 節的完整權限矩陣做滿。

# Gemini 503 重試：腦力激盪／探索紀錄
日期：2026-09-23 · 目標：修正 Gemini API 暫時性過載（503 UNAVAILABLE）導致的呼叫失敗
狀態：完成（已實作）
背景來源：使用者提供的實際 Supabase Edge Function log，`supabase/functions/_shared/providers/google.ts`

## 問題確認
使用者測試「各 AI 自己回復」功能後，貼出真實的 Supabase log：

```
詢問 Gemini 失敗 Error: {
  "error": {
    "code": 503,
    "message": "This model is currently experiencing high demand. Spikes in demand are usually temporary. Please try again later.",
    "status": "UNAVAILABLE"
  }
}
    at Object.generate (.../google.ts:149:15)
    at async consultGemini (.../gemini.ts:18:20)
    at async handleConsultOtherAi (.../worker-task-start/index.ts:298:23)
  status: 503
}
```

這是 Google 官方自己回報的暫時性過載，訊息明講「Spikes in demand are usually
temporary. Please try again later.」——跟金鑰、額度、程式邏輯都無關，也跟先前排查過的
「-flash 思考額度」「SSE 尾端事件遺失」等理論完全不同（那兩個是回應「空白」，這個是
回應直接 503 失敗）。不需要 grill-me 訪談：重試暫時性錯誤是標準、低風險的可靠度修正，
沒有需要使用者決策的取捨。

## 決策
1. **可重試的狀態碼**：429（RESOURCE_EXHAUSTED，短暫速率限制）與 503
   （UNAVAILABLE，暫時過載）。其他狀態碼（例如 400 金鑰無效、403 權限不足）不會自己
   好轉，直接照舊丟給呼叫端處理。
2. **重試次數與間隔**：最多重試 2 次，指數退避，起始延遲 700ms（700ms → 1400ms）。
3. **套用範圍**：`generate()`／`generateStream()` 共用同一個 `fetchWithGeminiRetry()`
   輔助函式，兩邊都要套用（`generateStream()` 也要把 `AbortSignal` 傳進 `sleep()`，
   讓使用者按「停止」時重試等待也能立即中斷，不會卡住）。
4. **不改變既有錯誤處理介面**：重試用完或狀態碼不可重試時，把原始 `Response` 原封不動
   回傳，讓既有的 `!res.ok` → `ProviderHttpError` 邏輯照舊運作，不用另外重寫一份。

## 實作
`supabase/functions/_shared/providers/google.ts`：
- 新增 `RETRYABLE_STATUSES`（`{429, 503}`）、`MAX_RETRIES = 2`、
  `RETRY_BASE_DELAY_MS = 700`。
- 新增 `sleep(ms, signal)`：支援 `AbortSignal` 中斷等待。
- 新增 `fetchWithGeminiRetry(url, init)`：包一層重試邏輯在 `fetch()` 外面。
- `generate()`、`generateStream()` 的 `fetch(...)` 呼叫都改成
  `fetchWithGeminiRetry(...)`。

不需要新的 migration（純 Edge Function 邏輯修改），跟著既有的
`deploy-functions` GitHub Actions 自動部署。

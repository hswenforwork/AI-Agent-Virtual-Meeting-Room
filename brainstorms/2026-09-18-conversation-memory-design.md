# 對話摘要記憶設計：腦力激盪／探索紀錄
日期：2026-09-18 · 目標：把「歷史對話摘要記憶」＋「房間資料保留/封存/刪除」這個延伸功能的設計問清楚、驗證假設，決定要不要做、做到什麼程度
狀態：「摘要記憶」核心設計已定案；「刪除開關／永久保留訊息／臨時聊天室」三項附加功能延到未來另開訪談
背景來源：
- `docs/MVP規劃-v2.md` 第 6.1 節「上線後發現、已記錄但先不做的項目」
- 原始 MVP 訪談：`brainstorms/2026-09-18-ai-agent-collab-room-mvp.md`
- 使用者透過另一個 AI（GPT）取得的「摘要＋最近訊息」混合模式設計提案（見下方摘要）

## 提案內容摘要（尚未確認，待訪談驗證）
使用者貼上的 GPT 提案，重點：
- Database 只保留最近 30-50 則完整訊息 + 一份持續更新的歷史摘要 + 使用者標記「必須永久保存」的訊息
- 流程：新訊息 → 儲存最近 50 則 → 超過 50 則就把舊訊息整理成摘要、更新一筆摘要、移除已摘要的舊訊息 → 繼續聊天
- Claude 每次收到：歷史摘要 + 最近 20-30 則訊息 + 使用者新問題
- 替代方案「完全不保存」：不經過 messages 資料表、不用 Realtime，對話視窗 → Edge Function → Claude → 直接回傳；缺點是重整消失、無法跨裝置、無法搜尋、AI 不記得
- 最終建議「可控的混合模式」：最多保留 50 則、超過先摘要再移除、記事本/待辦/檔案永久保存、提供「永久保留這則訊息」按鈕、提供「不保存對話」的臨時聊天室模式、所有刪除規則由使用者在設定中開啟、AI 不可自行決定

## 摘要／重要決策

**「對話摘要記憶」定案設計（Q1-Q6）：**

1. 無急迫性，純粹先把設計定案，之後才做（Q1）。
2. 摘要（產生/更新，不動原始訊息）可自動在背景做；「刪除原始訊息」是獨立的另一個開關，不會因為摘要完成就自動刪除（Q2）。
3. 觸發時機：使用者送訊息、輪到代理要回覆之前，若訊息數超過門檻，**先摘要再回覆**（同一次請求做完，這次回覆會比較慢），不做額外的背景排程機制（Q3）。
4. 門檻：**超過 50 則**觸發摘要；摘要完成後 AI 上下文＝**摘要＋最近 24 則**（沿用現有 `agent-run` 已經在用的數字）（Q4）。機制暫定：把「超出最近 24 則」的較舊訊息整理進摘要並跟既有摘要合併成一筆新摘要，訊息本身不刪除，下次再超過 50 則就重複同樣流程。
5. 摘要要能在畫面上看到、也要能手動編輯修正（低風險操作，比照記事本不需確認卡）（Q5）。
6. UI 放右側**獨立的第四個分頁「房間摘要」**，跟記事本/待辦事項/檔案夾平行（Q6）。

**助理建議（實作層級，尚未經使用者確認，之後實作時可再核對）：**
- 資料庫實作上，用一個欄位（例如 `rooms.summary text`）存單一持續更新的摘要即可，不需要另建歷史摘要表——因為 Q4 的機制是「合併成一筆新摘要」而非保留每次摘要的歷史版本。

**延後、未在本次訪談範圍內定案的項目（之後另開訪談）：**
- 「刪除舊訊息」開關要放在哪裡、怎麼觸發、刪除規則長怎樣
- 「永久保留這則訊息」按鈕
- 「不保存對話」的臨時聊天室模式

## 問答紀錄

### Q1：現在真的有遇到問題了，還是純粹先把方案想清楚？
- 問題：(a) 只是先把方案想清楚，目前沒有實際問題 (b) 已經有感覺到問題（AI 忘記脈絡或在意資料庫累積） (c) 其他原因
- 已記錄：使用者選 **(a) 只是先把方案想清楚**，目前沒有遇到實際的資料量或 AI 忘記脈絡問題。
- 影響：**沒有急迫性**，這次訪談的目的是把設計想清楚、記錄決策，不代表要馬上動手實作。可以把重點放在「長期正確的設計」上，不用為了趕時間妥協。

### Q2：自動摘要+刪除要預設自動，還是要手動開啟？
- 問題：(a) 預設自動運作 (b) 預設關閉，要手動去設定開啟 (c) 摘要可以自動做，但「刪除原始訊息」這個動作要另外開關
- 已記錄：使用者選 **(c)**。摘要（產生/更新摘要，不動原始訊息）可以自動在背景做，因為這是「新增」不是「刪除」，低風險；但「真的把舊訊息從資料庫刪掉」這個難復原的動作要另外一個獨立開關，不能因為摘要做完就自動連帶刪除。
- 影響：這代表系統設計上「摘要」與「刪除」是兩個獨立、解耦的動作，符合訪談 Q12 定的「低風險免確認、難復原才需要確認」原則。資料庫累積的問題（GPT 提到的 Database 持續增加）在使用者沒有另外打開刪除開關之前，**不會被這個功能解決**——這只解決「AI 忘記脈絡」的問題，不解決「資料庫容量成長」的問題，兩者要分開看待。

### Q3：摘要動作怎麼觸發？
- 問題：(a) 自動背景觸發，不影響聊天速度 (b) 順便處理：送訊息輪到代理回覆前，若超過門檻就先摘要再回覆，同一次請求 (c) 手動觸發，按按鈕才做
- 已記錄：使用者選 **(b) 順便處理**。代理要回覆之前，如果訊息數超過門檻，先做摘要、更新摘要，再產生回覆，使用者這次會等比較久，但實作最簡單（不需要額外的排程/背景任務機制）。
- 影響：這代表 `agent-run` 這個 Edge Function 的邏輯要擴充：組合上下文之前先檢查訊息數量，超過門檻就先呼叫供應商 API 做摘要（多一次 API 呼叫、多一點延遲與費用），摘要完成後才繼續原本「組合上下文→呼叫模型回答」的流程。不需要 Supabase Cron 或額外背景任務基礎設施，維持架構簡單。

### Q4：摘要觸發門檻與保留則數？
- 問題：(a) 沿用 GPT 建議：超過 50 則觸發摘要，AI 上下文變成「摘要＋最近 24 則」(b) 自訂數字 (c) 先不設固定數字，之後再調整
- 已記錄：使用者選 **(a)**。門檻 **50 則**觸發摘要；摘要完成後 AI 上下文＝**摘要＋最近 24 則**（沿用現有 `agent-run` 已經在用的 24 這個數字，不用改動）。
- 機制細節（待確認，暫定）：訊息數超過 50 時，把「超出最近 24 則保留範圍」的那些較舊訊息整理進摘要，並跟既有摘要合併成新的一筆摘要；訊息本身**不刪除**（除非使用者另外打開 Q2 的刪除開關）。下次再累積到超過 50 則，重複同樣流程，把新一批「超出 24 則」的訊息併入摘要。

### Q5：摘要要不要在畫面上看得到？
- 問題：(a) 要，可以直接看甚至編輯 (b) 不用，只給 AI 自己用 (c) 之後再說
- 已記錄：使用者選 **(a)**，要能在介面上看到摘要內容，而且要能手動編輯修正。
- 影響：這是一個新的 UI 需求，摘要不再只是後端內部資料，需要有對應的畫面呈現與編輯功能（低風險操作，比照記事本，直接編輯不需確認卡）。
- 待釐清：這個摘要要放在右側現有的分頁（記事本/待辦事項/檔案夾）裡面，還是要獨立出一個新分頁／新入口？→ 待下一題釐清

### Q6：摘要放獨立分頁還是塞進既有分頁？
- 問題：(a) 獨立新分頁「房間摘要」(b) 塞進記事本分頁 (c) 不佔分頁，用彈窗
- 已記錄：使用者選 **(a) 獨立新分頁**。右側工具會從「記事本／待辦事項／檔案夾」三個分頁，變成加上「房間摘要」共四個分頁。

### 收尾：範圍確認
- 問題：核心「摘要記憶」設計已經問得差不多，GPT 提案裡還有「永久保留訊息」按鈕、「臨時聊天室（不保存）」模式、刪除規則設定介面這幾個附加功能沒問，要不要現在一起問？
- 已記錄：使用者選擇**先把「摘要」這個核心設計定案，其他附加功能之後另外開訪談**。
- 這代表本次訪談到此告一段落，「摘要記憶」設計視為定案（見下方摘要），「刪除舊訊息開關」「永久保留訊息按鈕」「臨時聊天室模式」三項留待未來訪談，不在這次定案範圍內。

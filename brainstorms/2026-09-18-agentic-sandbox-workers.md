## 問答紀錄

### Q1：促成這個轉折的核心原因是什麼？
- 問題：(a) 原本需求還在，但真正想要的是「派工給會做事的代理」，需求變了/更清楚了 (b) 兩者都要，不同情境並存 (c) 被 GPT 的討論帶偏了，原本的痛點還是比較重要
- 已記錄：使用者原話——「我的情境是這樣的，代理工作，但可能會卡在某個bug無法解決，這時代理可以透過聊天室詢問另一位AI代理，該代理可以先幫忙測試與分析問題，並給出建議，再由原本的代理一建議繼續修正問題。」
- 解讀：這其實把「原本的多供應商互相補位」跟「新的工作型代理」**兩個想法接在一起**了——不是單純選 (a)(b)(c) 其中一個。具體情境是：一個「工作型代理」（有沙盒、在寫程式）遇到自己解決不了的 bug 時，會去問**另一個 AI 供應商**幫忙分析、給建議，工作代理再照建議繼續修。這代表「多供應商互相補位」這個原始核心痛點**沒有消失**，而是從「使用者手動丟問題給不同 AI」，進化成「工作代理卡住時，會去找另一個 AI 供應商幫忙分析」——某種程度上是原始痛點的「自動化版本」。
- 待釐清：這個「找另一位 AI 代理幫忙」的動作，是工作代理自己判斷「我卡住了、我要去問」（全自動），還是使用者看到代理卡住、自己手動 @ 另一個供應商去看？→ 下一題釐清

### Q2：誰決定工作代理要不要去問另一個 AI？
- 問題：(a) 工作代理自己判斷、全自動 (b) 使用者手動 @ 觸發 (c) 半自動：代理舉手示意，使用者核准後才真的介入
- 已記錄：使用者原話——「A，代理自己重複3次無法解決，就將問題資訊整理好，自動詢問另一位代理，不需要我介入。」
  - 選 **(a) 全自動**，機制具體化：工作代理**重複嘗試 3 次**還是解決不了，就自動把問題資訊整理好，主動詢問另一位代理，不需要使用者核准或介入。
- 影響：這是明確的「全自動代理間協作」，跟原始規劃文件（v1）與 v2 計畫裡「代理轉派需要核准」「避免無限代理循環」的保護機制（例如 6.4 節的轉派深度上限、agent.delegate 需要確認）方向不同——這裡使用者明確要的是「不用我介入」。技術上需要：①工作代理要能判斷「這次嘗試算不算成功」②要能計數「重複幾次」③失敗 3 次後要能自動組一份「問題摘要」交給另一個供應商④另一個供應商的回覆要能餵回給原本的工作代理繼續修。

### Q3：「沙盒」具體是什麼樣子？
- 問題：(a) 完整開發環境，類似 Claude Code，有檔案系統、能跑 bash、裝套件、跑測試 (b) 輕量程式碼執行，只需要跑一小段程式碼驗證邏輯 (c) 還沒想清楚，需要建議
- 已記錄：使用者選 **(a) 完整開發環境**，跟使用者現在跟 Claude Code 互動的這種環境等級一樣。
- 影響（助理判斷，重要）：這跟「呼叫 API 拿一段文字」是完全不同量級的基礎建設，不是能在 Supabase Edge Function 裡直接做到的事（Edge Function 沒有持久檔案系統、執行時間有限、不能跑任意 bash）。要做到「完整開發環境」等級的沙盒，實務上比較合理的路是**不要自己重新造一套容器/沙盒基礎建設**，而是直接串接 Anthropic 官方已經提供的 Claude Agent SDK / Claude Code Remote 這類「已經內建沙盒執行環境的代理服務」（這個訪談對話本身用的 Claude Code Remote 就是一個例子：真正有檔案系統、能跑 bash、能建立 PR）。這個方向需要使用者確認：**是否要用 Claude 官方的代理執行環境**，而不是自建 Docker/容器基礎建設？→ 待下一題釐清
- 待釐清：這種等級的沙盒環境，運算成本遠高於純文字 API 呼叫，跟原本 US$30/月的 AI API 預算是分開的兩件事，需要另外問預算。→ 下一題釐清

### Q4：沙盒要怎麼實現？
- 問題：(a) 直接串接 Claude 官方的代理執行環境（Claude Agent SDK / Claude Code Remote，建議選項）(b) 自建容器/沙盒基礎建設 (c) 還沒想清楚，先聽利弊分析
- 已記錄：使用者選 **(a) 直接串接 Claude 官方的代理執行環境（建議選項）**。
- 影響：
  1. 「工作代理」（真正動手寫程式、跑指令、部署的那個角色）本質上會綁定 Claude，因為目前只有 Claude 有這種現成的代理執行服務；GPT/Gemini 沒有對等的東西可以直接串。
  2. 這代表協作室裡會出現**兩種性質不同的代理**：「聊天/意見型代理」（現有的，呼叫各供應商 Messages API 拿文字回應，GPT/Claude/Gemini 都可以）跟「工作型代理」（真正動手做事，目前只能是 Claude 的代理執行環境）。
  3. 這種代理執行環境的運算成本，跟單純文字 API 呼叫是不同量級、分開計費的，需要另外確認預算（下一題）。

### Q5：工作型代理的運算成本，預算怎麼抓？
- 問題：(a) 先抓明確數字 (b) 不設硬上限，先做出來實際用過才知道，之後再抓預算 (c) 先不急著做，等其他穩定、預算有餘裕再說
- 已記錄：使用者選 **(b) 不設硬上限**，先做出來實際用過才知道大概花多少，之後再回頭抓預算。

### Q6：工作型代理跟現有純文字 `@Claude` 是什麼關係？
- 問題：(a) 完全取代 (b) 兩種分開，各自獨立觸發 (c) 看內容自動判斷是問題還是任務
- 已記錄：使用者原話——「c，如果ai判斷是任務可以詢問我是否開始執行或是使用skill」。
  - 選 **(c) AI 自動判斷**：同樣是 `@Claude`，AI 自己判斷這是單純問題還是任務。
  - **補充機制**：AI 判斷是「任務」的話，不會自動開工作階段，而是先詢問使用者「要不要開始執行」或「要不要用某個 skill」，等使用者確認才真的開始動手。
- 影響：這代表「開始一個工作階段」這個動作本身需要使用者核准（跟 Q2 的「工作中卡住 3 次後自動找其他 AI 幫忙」不一樣——那個是已經開工之後、工作階段內部的自動行為，不需要核准；**這裡是開工前的第一道關卡，需要核准**）。使用者提到「skill」這個詞，呼應了 Q4 選擇的「直接串接 Claude 官方代理執行環境」方向——Claude Code 本身就有 skill 機制，這個心智模型跟採用 Claude Agent SDK / Claude Code Remote 是一致的。

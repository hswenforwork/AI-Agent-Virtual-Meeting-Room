# AI 協作室轉型：有工作環境的代理（沙盒/子代理/寫程式/部署）：腦力激盪／探索紀錄
日期：2026-09-18 · 目標：釐清使用者「代理應該有自己的工作室（沙盒、子代理、寫程式、部署）」這個新願景，確認跟現有已上線 MVP（多供應商文字比較）的關係，找出架構落差
狀態：核心設計已定案（見下方摘要），尚未實作；範圍遠大於現有已上線的 v2 MVP，屬於下一個大階段的規劃
背景來源：
- `brainstorms/2026-09-18-ai-agent-collab-room-mvp.md`（原始 MVP 訪談：多供應商平行比較）
- `docs/MVP規劃-v2.md`（已實作並上線的 v2 規劃）
- `brainstorms/2026-09-18-conversation-memory-design.md`（剛完成的摘要記憶設計）
- 現有實作：`supabase/functions/agent-run/index.ts` 目前只是呼叫 Anthropic Messages API 拿一段文字回應，沒有沙盒執行環境、沒有子代理機制、沒有寫檔案/跑程式/部署能力

## 使用者原話
「我發現，目前這個工具與我想像中有不同，我希望在聊天室內的Ai代理，而不是純LLM，我希望我發送任務訊息，代理們在自己的工作室運作，包含沙盒、子代理、撰寫程式等工作，完成後再將成品上傳至聊天室的照片、檔案、記事本或部署到github。然後在聊天室內回報工作完成與交辦事項。」

## 摘要／重要決策

**「工作型代理」定案設計（Q1-Q10）：**

1. **動機**：不是拋棄「多供應商互相補位」的原始痛點，而是把它接到一個更具體的情境——工作代理（有沙盒、在寫程式）卡住時，自動去問另一個 AI 供應商分析、給建議（Q1）。
2. **卡住時的自動求助**：工作代理重複嘗試 **3 次**解決不了，自動整理問題資訊、主動詢問另一位代理，**不需要使用者核准**（Q2）。
3. **沙盒＝完整開發環境**，跟使用者現在用的 Claude Code 同等級（有檔案系統、能跑 bash、裝套件、跑測試）（Q3）。
4. **實現方式**：直接串接 **Claude 官方的代理執行環境**（Claude Agent SDK / Claude Code Remote），不自建容器/沙盒基礎建設（Q4）。**這代表「工作型代理」本質上綁定 Claude**，跟「聊天/意見型代理」（GPT/Claude/Gemini 都能用的純文字比較）是兩種不同性質的代理。
5. **預算**：不設硬上限，先做出來實際用過才知道大概花多少（Q5）。
6. **任務 vs 問題的判斷**：同樣是 `@Claude`，AI 自動判斷這是單純問題還是任務；判斷是任務的話，**先問使用者要不要開始執行／要不要用某個 skill**，使用者確認後才真的開工（Q6）——這是「開工前」的核准關卡，跟第 2 點「開工後卡住自動找人幫忙」是不同階段、不同規則。
7. **GitHub 部署範圍**：這個協作室專案本身優先，之後才擴充到任意指定的 repo（Q7）。
8. **回報方式**：特殊的**任務卡片**訊息類型，顯示狀態（進行中/完成/失敗）、變更內容、產出連結，不是一般文字訊息（Q8）。
9. **子代理**：就是 Claude Code 本身內建的 Task 工具機制，協作室不需要另外設計子代理的資料模型或 UI，全部包在同一張任務卡片裡（Q9）。
10. **產出歸檔**：工作代理完成後自動把產出（截圖、文件、程式碼檔案）存進檔案夾，自己決定分類，不需要使用者逐一核准（Q10）。

**✅ 原本標記的矛盾已解決**：使用者確認「有 Gemini 的免費 API key」。這代表 Q2「卡住 3 次自動詢問另一位代理」有真正的對象可問了——**Gemini 可以做為工作代理卡住時的求助對象**，不用再等 GPT。原本記錄在 `brainstorms/2026-09-18-ai-agent-collab-room-mvp.md` 的「GPT、Google 的 API key 都尚未申請」這件事，Google／Gemini 的部分已經不成立，OpenAI／GPT 仍然還沒有 key。

**與現有已上線 v2 MVP 的落差：**
- 現有 `agent-run` Edge Function 只呼叫 Anthropic Messages API 拿文字回應，完全沒有沙盒、沒有任務卡片、沒有「任務 vs 問題」判斷、沒有自動歸檔機制——這次訪談定案的設計目前**都還沒實作**，需要另外排一輪開發。
- 這比「對話摘要記憶」（`brainstorms/2026-09-18-conversation-memory-design.md`）的複雜度跟基礎建設需求都高出很多量級，建議視為獨立的下一個開發階段，不要跟摘要記憶功能混在一起做。

## 問答紀錄

### Q1：促成這個轉折的核心原因是什麼？
- 問題：(a) 原本需求還在，但真正想要的是「派工給會做事的代理」，需求變了/更清楚了 (b) 兩者都要，不同情境並存 (c) 被 GPT 的討論帶偏了，原本的痛點還是比較重要
- 已記錄：使用者原話——「我的情境是這樣的，代理工作，但可能會卡在某個bug無法解決，這時代理可以透過聊天室詢問另一位AI代理，該代理可以先幫忙測試與分析問題，並給出建議，再由原本的代理一建議繼續修正問題。」
- 解讀：這其實把「原本的多供應商互相補位」跟「新的工作型代理」**兩個想法接在一起**了——不是單純選 (a)(b)(c) 其中一個。具體情境是：一個「工作型代理」（有沙盒、在寫程式）遇到自己解決不了的 bug 時，會去問**另一個 AI 供應商**幫忙分析、給建議，工作代理再照建議繼續修。這代表「多供應商互相補位」這個原始核心痛點**沒有消失**，而是從「使用者手動丟問題給不同 AI」，進化成「工作代理卡住時，會去找另一個 AI 供應商幫忙分析」——某種程度上是原始痛點的「自動化版本」。
- 待釐清：這個「找另一位 AI 代理幫忙」的動作，是工作代理自己判斷「我卡住了、我要去問」（全自動），還是使用者看到代理卡住、自己手動 @ 另一個供應商去看？→ 下一題釐清

### Q2：誰決定工作代理要不要去問另一個 AI？
- 問題：(a) 工作代理自己判斷、全自動 (b) 使用者手動 @ 觸發 (c) 半自動：代理舉手示意，使用者核准後才真的介入
- 已記錄：使用者原話——「A，代理自己重複3次無法解決，就將問題資訊整理好，自動詢問另一位代理，不需要我介入。」
  - 選 **(a) 全自動**，機制具體化：工作代理**重複嘗試 3 次**還是解決不了，就自動把問題資訊整理好，主動詢問另一位代理，不需要使用者核准或介入。
- 影響：這是明確的「全自動代理間協作」，跟原始規劃文件（v1）與 v2 計畫裡「代理轉派需要核准」「避免無限代理循環」的保護機制（例如 6.4 節的轉派深度上限、agent.delegate 需要確認）方向不同——這裡使用者明確要的是「不用我介入」。技術上需要：①工作代理要能判斷「這次嘗試算不算成功」②要能計數「重複幾次」③失敗 3 次後要能自動組一份「問題摘要」交給另一個供應商④另一個供應商的回覆要能餵回給原本的工作代理繼續修。

### Q3：「沙盒」具體是什麼樣子？
- 問題：(a) 完整開發環境，類似 Claude Code，有檔案系統、能跑 bash、裝套件、跑測試 (b) 輕量程式碼執行，只需要跑一小段程式碼驗證邏輯 (c) 還沒想清楚，需要建議
- 已記錄：使用者選 **(a) 完整開發環境**，跟使用者現在跟 Claude Code 互動的這種環境等級一樣。
- 影響（助理判斷，重要）：這跟「呼叫 API 拿一段文字」是完全不同量級的基礎建設，不是能在 Supabase Edge Function 裡直接做到的事（Edge Function 沒有持久檔案系統、執行時間有限、不能跑任意 bash）。要做到「完整開發環境」等級的沙盒，實務上比較合理的路是**不要自己重新造一套容器/沙盒基礎建設**，而是直接串接 Anthropic 官方已經提供的 Claude Agent SDK / Claude Code Remote 這類「已經內建沙盒執行環境的代理服務」（這個訪談對話本身用的 Claude Code Remote 就是一個例子：真正有檔案系統、能跑 bash、能建立 PR）。這個方向需要使用者確認：**是否要用 Claude 官方的代理執行環境**，而不是自建 Docker/容器基礎建設？→ 待下一題釐清
- 待釐清：這種等級的沙盒環境，運算成本遠高於純文字 API 呼叫，跟原本 US$30/月的 AI API 預算是分開的兩件事，需要另外問預算。→ 下一題釐清

### Q4：沙盒要怎麼實現？
- 問題：(a) 直接串接 Claude 官方的代理執行環境（Claude Agent SDK / Claude Code Remote，建議選項）(b) 自建容器/沙盒基礎建設 (c) 還沒想清楚，先聽利弊分析
- 已記錄：使用者選 **(a) 直接串接 Claude 官方的代理執行環境（建議選項）**。
- 影響：
  1. 「工作代理」（真正動手寫程式、跑指令、部署的那個角色）本質上會綁定 Claude，因為目前只有 Claude 有這種現成的代理執行服務；GPT/Gemini 沒有對等的東西可以直接串。
  2. 這代表協作室裡會出現**兩種性質不同的代理**：「聊天/意見型代理」（現有的，呼叫各供應商 Messages API 拿文字回應，GPT/Claude/Gemini 都可以）跟「工作型代理」（真正動手做事，目前只能是 Claude 的代理執行環境）。
  3. 這種代理執行環境的運算成本，跟單純文字 API 呼叫是不同量級、分開計費的，需要另外確認預算（下一題）。

### Q5：工作型代理的運算成本，預算怎麼抓？
- 問題：(a) 先抓明確數字 (b) 不設硬上限，先做出來實際用過才知道，之後再抓預算 (c) 先不急著做，等其他穩定、預算有餘裕再說
- 已記錄：使用者選 **(b) 不設硬上限**，先做出來實際用過才知道大概花多少，之後再回頭抓預算。

### Q6：工作型代理跟現有純文字 `@Claude` 是什麼關係？
- 問題：(a) 完全取代 (b) 兩種分開，各自獨立觸發 (c) 看內容自動判斷是問題還是任務
- 已記錄：使用者原話——「c，如果ai判斷是任務可以詢問我是否開始執行或是使用skill」。
  - 選 **(c) AI 自動判斷**：同樣是 `@Claude`，AI 自己判斷這是單純問題還是任務。
  - **補充機制**：AI 判斷是「任務」的話，不會自動開工作階段，而是先詢問使用者「要不要開始執行」或「要不要用某個 skill」，等使用者確認才真的開始動手。
- 影響：這代表「開始一個工作階段」這個動作本身需要使用者核准（跟 Q2 的「工作中卡住 3 次後自動找其他 AI 幫忙」不一樣——那個是已經開工之後、工作階段內部的自動行為，不需要核准；**這裡是開工前的第一道關卡，需要核准**）。使用者提到「skill」這個詞，呼應了 Q4 選擇的「直接串接 Claude 官方代理執行環境」方向——Claude Code 本身就有 skill 機制，這個心智模型跟採用 Claude Agent SDK / Claude Code Remote 是一致的。

### Q7：部署到 GitHub 是指哪個 repo、用誰的身份？
- 問題：(a) 就是這個協作室專案本身 (b) 任意指定的 repo，用途更廣 (c) 兩者都要，這個協作室優先
- 已記錄：使用者選 **(c) 兩者都要，這個協作室專案本身是第一優先、最先要能動的使用情境**。
- 影響：MVP 實作順序上，「工作代理能對這個協作室 repo 本身開 PR」應該是第一步驗證的情境（畢竟這個 repo 本身現在就是使用者在維護的目標），「對任意指定 repo 動手」是之後的擴充。身份/權限機制（例如 GitHub App、per-task 授權範圍）留到實作階段再細化。

### Q8：工作代理完成任務後怎麼回報到聊天室？
- 問題：(a) 特殊的任務卡片，顯示狀態/變更內容/產出連結 (b) 就是一般聊天訊息 (c) 兩者都要：過程用文字即時更新，完成時出卡片總結
- 已記錄：使用者選 **(a) 特殊的任務卡片（建議選項）**。任務卡片要能顯示任務狀態（進行中/完成/失敗）、做了哪些變更、產出的檔案/連結（例如 PR 網址）。
- 影響：這代表 `messages` 這張表（或另一張新表）需要能表示「任務卡片」這種結構化訊息類型，不是單純的文字內容；前端也需要一個新的訊息渲染元件專門顯示任務卡片，跟一般文字泡泡、系統提示是三種不同的呈現方式。

### Q9：「子代理」具體想像中是什麼？
- 問題：(a) 就是 Claude Code 本身的 Task 工具機制，內部拆解子任務、包在同一張任務卡片裡 (b) 使用者看得到、能個別互動的獨立子代理 (c) 還沒想清楚，只是隨口提到的詞
- 已記錄：使用者選 **(a) 就是 Claude Code 本身的 Task 工具機制（建議選項）**。
- 影響：不需要在協作室自己的資料庫/UI 裡另外設計「子代理」這個概念——子代理的拆解、派工、回報都是 Claude Code / Claude Agent SDK 內部已經處理好的事，協作室這邊只需要接收「工作型代理」整體的進度與最終結果，包進 Q8 的任務卡片裡即可，不需要額外的資料模型。這大幅簡化了協作室這邊要做的事。

### Q10：工作代理產出的東西要放進檔案夾，誰來觸發？
- 問題：(a) 工作代理自己決定放哪個分類、直接執行 (b) 任務卡片附連結，使用者自己決定要不要存進檔案夾
- 已記錄：使用者選 **(a) 工作代理自己決定放哪個分類（建議選項）**，直接執行，事後在任務卡片看得到連結。
- 影響：這代表「上傳產出到檔案夾」屬於低風險自動化操作（比照 Q12 原則：新增類的動作可以自動做），不需要使用者逐一核准；工作代理需要能呼叫協作室既有的 `file-register` 這類機制，把產出寫進 `files` 表。目前 v2 的檔案夾還沒有「相簿」這個獨立分類（v2 MVP 延後了相簿功能），所以「照片」類產出目前應該先歸進檔案夾，等相簿功能之後做了再分流。

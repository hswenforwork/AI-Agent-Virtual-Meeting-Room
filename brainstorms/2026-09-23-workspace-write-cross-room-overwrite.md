# 修正：跨聊天室記事本被誤判成「更新既有記事」而覆蓋掉
日期：2026-09-23 · 目標：修正使用者回報「不同對話窗共用記事本，原本的記事本內容會被覆蓋掉，而不是新建一個」
狀態：完成

## 問題

記事本／待辦事項是跨聊天室共用的（`owner_id` 歸屬使用者本人，不分房間，見
`brainstorms/2026-09-23-gpt-audit-followups.md` Q1）。使用者在某個聊天室請 AI 記一則新的
內容，結果 AI 沒有新增一筆，而是把**另一個聊天室裡本來就存在的記事**的內容覆蓋掉了。

## 根因

`workspaceWrite.ts` 的 `classifyMessage()` 讓分類模型自己判斷這次是 `create_note`
還是 `update_note`；`update_note` 一旦被選中，`applyWorkspaceWrite()` 會直接
`update patch` 整個 `content` 欄位覆蓋過去（`parseWorkspaceWrite()` 不會做任何「這真的是
同一件事嗎」的把關，完全信任模型回傳的 `id`）。

模型判斷用的既有項目清單（`fetchWorkspaceMatchItems()` → `buildMatchItemsText()`）原本
**只給標題**，而且沒有標題的記事一律顯示成籠統的「未命名記事」。這份清單本來就是
「使用者所有聊天室的所有記事」（不是只有目前這個房間的），一旦使用者這次也沒有明確標題，
分類模型很容易看到清單裡有一筆同樣叫「未命名記事」的既有項目，就誤判成「這應該是同一筆」，
選了 `update_note` 而不是 `create_note`——尤其是在跨聊天室的情境下，模型完全沒有其他上下文
可以分辨兩者其實毫無關係。

## 修正

1. **`WorkspaceMatchItem` 補上內容預覽**（`fetchWorkspaceMatchItems()` 改成也查詢
   `notes.content`，取前 40 字當 `preview`，顯示進 `buildMatchItemsText()` 給模型看）。
   讓模型除了標題以外，多一個能判斷「這真的是同一筆嗎」的依據，而不是只能靠一個
   完全没有辨識度的「未命名記事」標題瞎猜。
2. **收緊分類 prompt（`WORKSPACE_WRITE_SPEC`）**：明確告知模型 `update_note`/`update_task`
   會直接覆蓋掉使用者的舊資料，選錯會讓資料憑空消失，一定要非常保守——
   - 只有使用者這則訊息本身明確在講修改/更新/補充一筆**既有**的東西時才能用 update；
     單純是在講一件新事情，即使清單裡剛好有標題或內容相似的項目（尤其是預設的
     「未命名記事」），也一律當新的一筆處理。
   - 只有使用者的話能明確指出是哪一筆、且清單裡有清楚對應的單一項目時才配對；
     只要有任何不確定，一律用既有的 `clarify` 機制反問，不能因為「這是唯一一筆」
     或「看起來像」就直接選它。
   - 順便補一句提醒：這份清單可能包含其他聊天室、跟這次對話主題完全無關的項目。

## 已知取捨

- 這是 prompt 層級的行為調整，不是結構性保證——模型仍然可能判斷錯誤，只是把「誤判成
  update」的機率大幅降低（多了內容預覽可以比對、prompt 也明確要求優先選 create／
  不確定就 clarify）。如果之後還有類似回報，下一步可以考慮把 `update_note`／
  `update_task` 也放進 `approval_requests` 的核准流程（目前只有 `file.delete`
  這種高風險操作才會經過核准；見 `approval-decide/index.ts` 開頭註解），或是在
  UI 上讓「更新記事」的確認訊息附帶「更新前」的內容片段，方便使用者馬上發現誤判並
  回報。這次先用改動範圍較小的 prompt 修正，之後有更多實際案例再評估要不要加上
  結構性的保護機制。
